## What review found

### Raised by the first review, and sent to repair

- **A retry that arrives while the first attempt is still in flight is not deduplicated, so it double-charges** (high)
  - Requirement: The idempotency key must lock/reserve on first receipt, before the upstream call is made, so a second attempt with the same key that arrives before the first completes is rejected or made to wait rather than executed. This is the exact scenario the ticket is written to prevent ('the client's connection drops, it retries the charge... we bill the customer twice') — the client retries while its original request is still being processed server-side.
  - Evidence: app/charges.py post_charge: the cache lookup happens first, but `self._idempotency_cache[idempotency_key] = result` is only written *after* `self._execute(params)` returns. Nothing marks the key as 'in progress' before calling `_execute`. `before_execute` (called inside `_execute`) is documented as the point where 'Operations monkey-patches this in staging to inject latency and to replay traffic' — i.e. overlapping calls during that window are an anticipated real scenario, and the current code has no guard against it.
  - If shipped: A customer whose retry (automatic, from the mobile SDK per the ticket) reaches the server before the first attempt's response is recorded gets charged twice — the exact double-charge bug this ticket exists to fix.

- **A transient processor failure (e.g. simulate='processor_down') is cached under the idempotency key forever, so retries never actually re-attempt the charge** (high)
  - Requirement: Standard idempotency-key semantics (as implemented by every major payments API this feature is modeled on) do not permanently pin a client to a transient/definitive-failure response for a key; a retry after a failed attempt must be allowed to actually re-attempt the charge, otherwise clients can never successfully complete a purchase once the first attempt hit a 5xx.
  - Evidence: app/charges.py post_charge: `result = self._execute(params)` is stored into `self._idempotency_cache[idempotency_key]` unconditionally, including when `_execute` returns `500, {"error": "processor unavailable", ...}` (the `simulate="processor_down"` branch that the provided `_execute` deliberately supports). Every subsequent call with that key replays the cached 500 forever, regardless of processor recovery.
  - If shipped: A customer whose first attempt hits a transient processor outage is permanently stuck: every retry with the same idempotency key (which is exactly what a retrying SDK would send) returns the same 500 forever, even after the processor recovers. The charge can never succeed unless the client fabricates a new key — defeating the point of idempotency and leaving the customer unable to complete checkout.

- **Reusing an idempotency key with a different request body silently returns the first request's cached response instead of being rejected** (high)
  - Requirement: Idempotency keys must be scoped to a specific request payload; reusing a key with a different body is a client error and must not silently return the stored response for the original (different) request.
  - Evidence: app/charges.py post_charge: the cache is keyed only on `idempotency_key`, with no comparison against the incoming `params`. `if idempotency_key is not None and idempotency_key in self._idempotency_cache: return self._idempotency_cache[idempotency_key]` returns the first response verbatim no matter what `amount`/`currency` the second call sends.
  - If shipped: A caller that (accidentally or deliberately) reuses a key with a larger amount gets back a 200 'succeeded' response describing the original, smaller charge — e.g. charge $1 with key X, then charge $100,000 with key X, and the API reports success for $1 while implying the larger charge went through. This is a billing/reconciliation hazard and a signoff blocker for any payments/security reviewer, since it lets a stored low-value response stand in for an unrelated, unauthorized-amount request.


### Still flagged after the repair pass

- **A failure before the processor is contacted permanently locks the idempotency key, blocking all future retries** (high)
  - Requirement: The ticket's own motivating scenario: 'the client's connection drops, it retries the charge, and we bill the customer twice' — the fix must let a legitimate retry go through when the prior attempt never reached the processor. `self.executed` is defined as the ledger of what the processor 'actually attempted'; a key that maps to zero entries in `self.executed` must not be permanently unusable.
  - Evidence: app/charges.py: post_charge sets `in_progress=True` in the cache before calling `_execute`, but only clears/updates the record in the code that runs *after* `result = self._execute(params)` returns. `_execute` calls `self.before_execute()` before it appends anything to `self.executed` (line 84-91), and `before_execute` is explicitly documented as PROVIDED but externally monkey-patched ('Operations monkey-patches this in staging to inject latency and to replay traffic'). If that call raises (network timeout, injected fault, or any exception before the ledger append), the exception propagates out of post_charge, the `del`/update block for the idempotency cache is never reached, and the record is left with in_progress=True forever with no charge ever recorded in self.executed.
  - If shipped: A transient failure while dialing the processor (exactly the kind of failure the ticket exists to survive) leaves the customer's idempotency key stuck in 'in progress' state permanently. Every subsequent retry with that key -- including the mobile SDK's automatic retry the ticket is written for -- gets a 409 forever, and the charge can never be completed, even though no money was ever attempted to move. This is worse than the bug being fixed: instead of a double charge, the customer can never be charged at all under that key.

- **No locking around the reserve-then-execute sequence lets two concurrent requests with the same key both reach the processor** (high)
  - Requirement: Idempotency-key semantics (as implemented by every real payments API this ticket is modeling, e.g. Stripe's Idempotency-Key behaviour) require that concurrent requests sharing a key be serialized so only one ever reaches the processor. The code's own comment states the intent: 'Reserve the key before contacting the processor so a retry that arrives while this attempt is still in flight is rejected instead of executed' -- this guarantee is not actually enforced under concurrency.
  - Evidence: app/charges.py post_charge: `record = self._idempotency_cache.get(idempotency_key)` and the subsequent `self._idempotency_cache[idempotency_key] = _IdempotencyRecord(...)` are two separate, unsynchronized operations with no lock. If two threads/workers both read the cache and both observe no existing record before either one writes its reservation, both proceed to `_execute`, both append to `self.executed`, and the second reservation silently overwrites the first.
  - If shipped: Under real concurrency (e.g. the mobile SDK firing a retry just as the original request is still being dispatched by a worker pool, or two app server processes/threads racing on the same key), the customer is charged twice -- the exact double-charge bug PAY-208 was opened to eliminate, now moved from 'client retries after a dropped connection' to 'two near-simultaneous attempts with the same key'.
