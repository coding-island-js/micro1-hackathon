## What review found

### Raised by the first review, and sent to repair

- **A UTF-8 BOM on the first header cell causes the entire file to be rejected as missing all required columns** (high)
  - Requirement: Ticket: "The files come from the customer's own systems — HR exports, spreadsheets, whatever they've got — so we don't control how they're produced." Excel's own "CSV UTF-8" export (the most common Windows path for producing a CSV from a spreadsheet) writes a leading U+FEFF byte-order-mark, which decodes to a literal \ufeff character prepended to the first header name.
  - Evidence: app/importer.py:47-53 strips whitespace from header cells but never strips a leading BOM character, so the first header cell becomes '\ufeffemail' instead of 'email'. The membership check `column not in header` then fails to find 'email' at all, and ALL of REQUIRED_COLUMNS are reported missing even though the column is clearly present to a human looking at the file.
  - If shipped: An admin uploads an Excel-exported CSV (a completely normal, unmodified export) and the tool rejects the whole 340-row file with 'missing required column(s): email, name, team', even though every column is there. The admin has no way to fix this without knowing to re-save the file in a different encoding, and support gets a ticket for what looks like a total tool failure.

- **Header column matching is case-sensitive, so 'Email'/'Name'/'Team' (or any differently-cased header) is treated as entirely missing** (medium)
  - Requirement: Ticket: files come from arbitrary customer systems with no control over format; a reasonable reading of "email, name and team must be present" is that the required columns are present by name, not that they must appear in one exact case.
  - Evidence: app/importer.py:48 does `column not in header` with no case normalization, even though the header cells are already being stripped (line 47) — evidence the code was reaching for some tolerance of messy input but stopped short of case.
  - If shipped: An HR export or spreadsheet with title-cased or upper-cased column headers (very common — 'Email', 'Name', 'Team', or 'EMAIL ADDRESS') is rejected outright as missing all three required columns, even though the data is complete and correct.

- **Leading/trailing whitespace is used to validate a field but is not stripped from the value actually stored in result.users** (medium)
  - Requirement: Internal consistency of the implementation's own validation logic: email/name/team are validated via `.strip()` (importer.py:68-75) to decide pass/fail, but the raw, un-stripped value is what gets written into the record and returned to the caller.
  - Evidence: app/importer.py:65 builds `record = dict(zip(header, row))` from the raw row values before any stripping, and the `.strip()` calls in the validation block only affect the truthiness check, not what's stored. So ' ada@example.com ' passes validation (because `.strip()` is truthy and contains '@') but is stored with the surrounding whitespace intact.
  - If shipped: Spreadsheet exports very commonly have padding whitespace in cells. A user is created with email ' ada@example.com ' (with spaces) in the downstream system, which then fails to match on login, fails uniqueness checks against a properly-formatted address, or fails delivery when an invite email is sent to it.

- **Two rows with the same email address are both imported as separate users with no error or dedup** (low)
  - Requirement: Implicit requirement of a 'user import': email is the natural unique identity key, and a bulk import feature onboarding customers is exactly the case (HR exports, merged spreadsheets) where the same person appears twice under slightly different rows.
  - Evidence: app/importer.py has no duplicate-detection logic anywhere in the row loop (lines 55-83); every syntactically valid row is appended to `result.users` regardless of whether its email already appeared earlier in the same file.
  - If shipped: A 340-row onboarding CSV that lists the same person twice (common when merging exports from two source systems, or a copy-paste error) silently creates two user accounts for one person, with no error surfaced to the admin doing the review — this is exactly the kind of row 'that can't be imported' cleanly that the ticket says should be reported back instead of silently accepted.


### Still flagged after the repair pass

- **Duplicate header column names silently overwrite each other, corrupting imported records** (high)
  - Requirement: A row that cannot be imported must go to errors, not be silently corrupted; the contract promises users are 'keyed by the header column names' with no mention of data loss on collision. This is also basic CSV-parsing correctness: RFC 4180-style CSV has no guarantee of unique header names, and a robust importer from untrusted external files must not let one column silently overwrite another required field's value with no error surfaced.
  - Evidence: app/importer.py:77 builds `record = dict(zip(header, row))`, and `column_lookup` (line 61-63) resolves each required column to only the *first* header cell with that name via `lower_header.index(...)`. When the header has two columns with the same name (e.g. `email,name,team,name` -- easy to get from merged/hand-edited HR exports), `dict(zip(...))` keeps the *last* column's value under that key, so `record.get(name_key)` returns the last column's data. The row is imported with no error, silently substituting an unrelated field's contents for the real name.
  - If shipped: An admin uploads a customer HR export that happens to have two columns sharing a name (common after a spreadsheet merge or an accidental duplicate export column). The importer reports zero errors and creates user accounts with wrong names/teams pulled from the wrong column, with no indication anything went wrong -- corrupted data enters the system silently and admins have no signal to check.

- **Duplicate-email detection is case-sensitive, letting the same person be imported twice** (medium)
  - Requirement: Email addresses are conventionally treated as case-insensitive for identity/dedup purposes (RFC 5321 makes the domain case-insensitive, and in practice virtually every mail and auth system treats the whole address as case-insensitive for matching); a bulk-import feature whose job is to catch unimportable/duplicate rows should not let cosmetic case differences bypass its own duplicate check.
  - Evidence: app/importer.py:65,101-104 -- `seen_emails` is compared and stored using the raw, unmodified `email` string (only `.strip()`ped, never case-folded), so `Ada@Example.com` and `ada@example.com` are treated as two distinct emails and both rows are imported.
  - If shipped: HR exports frequently have inconsistent casing (e.g. one row from a directory sync in Title Case, another hand-typed in lowercase). The importer creates two separate user records for the same person instead of flagging the second as a duplicate, leading to duplicate accounts, split permissions/history, and admin cleanup work later.
