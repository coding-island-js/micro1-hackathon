## What review found

### Raised by the first review, and sent to repair

- **Requesting a second reset email does not invalidate the first token** (medium)
  - Requirement: OWASP Forgot Password Cheat Sheet: generating a new reset token should invalidate any previously issued, still-valid token for that account, so only the most recently issued link is usable
  - Evidence: app/auth.py request_reset() stores each token under its own key in self._resets keyed only by token, with no lookup/removal of any prior token belonging to the same email before inserting the new one.
  - If shipped: A user who clicks 'resend' (e.g. because the first email was slow or went to spam) leaves two live reset links outstanding. If the first email is later found in an inbox, forwarded, cached by a mail scanner, or intercepted, it still resets the account's password even though the user believes only the newest link is valid — a stale-credential account-takeover vector.

- **A second outstanding token can reset the password again after the account was already successfully reset via another token** (high)
  - Requirement: OWASP Forgot Password Cheat Sheet: all outstanding password-reset tokens for an account must be invalidated once the password has been successfully changed, so a leaked/old link cannot be used to overwrite a password the legitimate user has already changed
  - Evidence: app/auth.py reset_password() only deletes the single token it was called with (`del self._resets[token]`); it never scans self._resets for other entries whose email matches and removes them after a successful password change.
  - If shipped: If two reset emails were ever issued for the same account (resend, double-click, race), successfully resetting the password with one token does not kill the other. Anyone who later obtains that other still-unexpired token (old email in an inbox, browser history, proxy log) can reset the password again within the TTL window, silently undoing the legitimate user's password change — a durable account-takeover path.


### Still flagged after the repair pass

- **reset_password races on the same token and crashes with an unhandled KeyError under concurrent use** (high)
  - Requirement: Single-use token consumption must be an atomic check-then-consume operation; a service backing an HTTP endpoint must not throw an unhandled exception when two requests race on the same token (double-submit, retry-after-timeout-while-first-succeeded, or an attacker replaying a captured link at the same moment as the legitimate user).
  - Evidence: app/auth.py:113-120 does `entry = self._resets.get(token)` then, only after that, unconditionally `del self._resets[token]`. These two steps are not atomic. If two calls to reset_password(token, ...) interleave between the get and the del (e.g. two concurrent requests, or a client retry landing while the first request is still in flight), both see a valid entry, both pass the `entry is None` check, and the second `del self._resets[token]` raises `KeyError` because the first call already removed it. There is no locking anywhere in the class.
  - If shipped: In any deployment where PasswordResetService is shared across concurrent requests (any real web server), a double-submit or a client retry racing with the original request turns a normal single-use-token rejection into an unhandled 500 error instead of a clean 'invalid token' response, and can also allow two different passwords to be set from one token depending on interleaving.

- **request_reset's fast-path for unregistered emails leaks account existence via response timing** (medium)
  - Requirement: OWASP Forgot Password Cheat Sheet: the response (including its timing) must not differ based on whether the submitted email is registered, so an attacker cannot enumerate valid accounts. The code's own comment states this exact intent.
  - Evidence: app/auth.py:94-97: `if email not in self.users: # Don't reveal whether an email is registered. return` -- this returns immediately doing a single dict lookup, whereas the registered-email path (lines 99-111) does token invalidation, cryptographic token generation, a dict write, string formatting, and a mailer call. Measured directly: 500 calls to a registered email took ~40x longer than 500 calls to an unregistered one.
  - If shipped: An attacker probing the forgot-password endpoint can distinguish registered from unregistered emails purely by measuring response latency, defeating the stated goal of not revealing account existence and enabling account/email enumeration for phishing or credential-stuffing targeting.
