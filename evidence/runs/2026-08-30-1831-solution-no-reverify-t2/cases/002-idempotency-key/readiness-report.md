## What review found

### Raised by the first review, and sent to repair

- **No in-progress lock: two simultaneous requests with the same key both charge** (high)
  - Requirement: An idempotency-key implementation must serialize concurrent requests carrying the same key -- either block the second until the first completes, or reject it (e.g. 409 'request in progress') -- so that two attempts in flight at once cannot both reach the processor.
  - Evidence: app/charges.py:89-102 -- the cache is only written *after* `_execute` returns (line 99-100). The check-then-execute-then-store sequence has no lock or in-progress marker. Two calls to `post_charge` with the same key, made before the first has finished, both pass the `idempotency_key in self._idempotency_cache` check as a miss and both call `_execute`.
  - If shipped: This is precisely the double-charge scenario the ticket exists to fix (PAY-208 cites three double-charge incidents), just at the concurrency layer instead of the sequential-retry layer: a client that fires a retry while the original request is still in flight (common with mobile SDKs and aggressive timeouts) bills the customer twice.

- **A transient processor failure (5xx) is cached permanently under the key, so the same key can never succeed** (high)
  - Requirement: Idempotency-key caching must only pin the terminal, successful outcome of a request. Retryable/errored attempts (5xx, processor-down, timeouts) must not be memoized -- the client must be able to retry the same key and have the charge actually attempted again.
  - Evidence: app/charges.py:97-100 -- `result = self._execute(params)` is stored into `self._idempotency_cache[idempotency_key]` unconditionally, including when `_execute` returns `500, {'error': 'processor unavailable', ...}` (line 83-84). Any later call with the same key returns the cached 500 without ever calling `_execute` again.
  - If shipped: If the upstream processor is briefly down on the first attempt, every subsequent retry with that idempotency key -- exactly what the mobile SDK's automatic retry does, per the ticket -- gets replayed the stale 500 forever. The charge can never succeed on that key; the customer is never billed even though they should be, and support gets a new class of ticket ('my payment never goes through') to replace the double-charge ones.

- **Same key with different request body silently replays the old response instead of erroring** (medium)
  - Requirement: Documented idempotency-key semantics (e.g. Stripe: 'if a key is reused for a different request, the API returns a 400 with an error') require the key to be bound to the specific request payload; reuse with mismatched parameters must be rejected, not silently satisfied from cache.
  - Evidence: app/charges.py:90-91 -- the cache lookup is keyed only by `idempotency_key`; `params` is never compared to what was stored on the first call for that key.
  - If shipped: A client bug (or an attacker) that reuses a key with a different `amount`/`currency` gets back the first charge's result for a request that was never actually executed with those parameters -- e.g. a $5 charge silently 'succeeds' while the response reports the original $25 charge, or vice versa, corrupting reconciliation between the client's records and what was actually billed.

- **Idempotency cache entries never expire and key size is unvalidated** (medium)
  - Requirement: Idempotency keys are documented to be honored only for a bounded retention window (Stripe: 24 hours), after which they may be reused for a new request; a production implementation must expire or evict entries rather than retain every key indefinitely.
  - Evidence: app/charges.py:58 declares `self._idempotency_cache: dict[str, tuple[int, dict]]` with no eviction path anywhere in `post_charge`. The `Clock` is injected specifically for time-based logic per the ticket ('take time from the injected Clock'), but `clock.now()` is never read in `post_charge` and no TTL/expiry exists. `validate_params` also never bounds the size of `idempotency_key` itself.
  - If shipped: The cache grows without bound for the lifetime of the process -- an unbounded memory leak under sustained traffic, and a low-effort DoS vector if a client sends large or high-cardinality keys, since neither key length nor cache size is ever checked or capped.
