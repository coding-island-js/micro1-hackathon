## What review found

### Raised by the first review, and sent to repair

- **reset_password is not atomic: concurrent use of the same token can double-apply or crash** (high)
  - Requirement: A password reset token must be redeemable exactly once, with consumption atomic against concurrent use (OWASP Forgot Password Cheat Sheet: token must be single-use; standard req for any one-time-use credential).
  - Evidence: app/auth.py:110-127 — reset_password() does `entry = self._tokens.get(token)`, then later `user.password_hash = ...` and `del self._tokens[token]` with no lock. Two threads/requests racing on the same still-valid token can both pass the initial `entry is None` check before either deletes: both set the password (last write wins, non-deterministic), and the second `del self._tokens[token]` raises an unhandled KeyError once the first thread has already removed it.
  - If shipped: In any threaded/async production deployment (e.g. WSGI with multiple worker threads, or a user double-clicking/retrying the reset-confirm request), a double submission of the same valid token either crashes the request with an uncaught KeyError (500 to the user) or silently applies two different passwords in an undefined order, leaving the user unsure which password is actually active.

- **Older outstanding reset tokens remain valid after a new request or after a successful reset** (high)
  - Requirement: OWASP Forgot Password Cheat Sheet / common password-reset lifecycle rule: issuing a new reset token should invalidate previously issued unused tokens for that account, and a successful password change should invalidate all other outstanding reset tokens for that account.
  - Evidence: app/auth.py:94-108 (request_reset) stores each new token keyed by itself without removing any prior token issued for the same email; app/auth.py:110-127 (reset_password) only deletes the one token that was redeemed, leaving any other still-unexpired tokens for that user active.
  - If shipped: If a user clicks 'forgot password' twice (e.g. because the first email was slow to arrive) both links stay live for an hour; whichever is used first to change the password does not revoke the other, so a second party who obtained the earlier email (an old inbox, a forwarded message, a compromised mail account) can still reset the password to a value of their choosing after the legitimate user has already 'secured' the account.

- **reset_password accepts any new_password, including empty string** (medium)
  - Requirement: NIST SP 800-63B §5.1.1.2 minimum length (8 chars) for memorized secrets used during a credential reset; a password-reset endpoint is a security boundary and must enforce the same minimum policy as account creation.
  - Evidence: app/auth.py:110-127 — new_password is passed straight into hash_password() with no length or emptiness check.
  - If shipped: A user (or attacker who obtained a valid token) can set the account password to '' or a single character, silently downgrading account security below whatever policy is enforced at signup, since the reset path bypasses it entirely.

- **request_reset does an exact-string user lookup, so a differently-cased but valid email silently gets no email** (medium)
  - Requirement: Common email-address handling convention (RFC 5321 domain part is case-insensitive, and virtually all mail providers treat the local part as case-insensitive too) — a self-service flow that identifies accounts by email must normalize case before lookup.
  - Evidence: app/auth.py:94-97 — `self.users.get(email)` does a raw dict lookup with no normalization; if the stored key is 'ada@example.com' and the user types 'Ada@Example.com', `user is None` and the function returns silently.
  - If shipped: A legitimate user who enters their email with different casing (very common — many clients auto-capitalize the first letter, or the user just doesn't remember the exact casing they signed up with) gets no error and no email, and has no way to tell whether the flow succeeded, leading directly to more support tickets — the exact problem this ticket exists to eliminate.

- **No throttling on request_reset lets one caller trigger unlimited reset emails** (medium)
  - Requirement: NIST SP 800-63B §5.2.2 / OWASP Forgot Password Cheat Sheet: rate-limit reset requests per account and per source to prevent abuse (mail-bombing, token-guessing amplification).
  - Evidence: app/auth.py:94-108 — request_reset has no counter, cooldown, or Clock-based throttle; it will happily issue a fresh token and send a fresh email on every call.
  - If shipped: An attacker can script repeated calls to request_reset for a victim's email to flood their inbox (harassment / mail-bombing) or to keep a large pool of simultaneously valid tokens outstanding (compounding the stale-token-invalidation gap above), with the account service acting as an open mail relay for the abuse.

- **Expired, never-redeemed tokens are never purged from memory** (low)
  - Requirement: Basic resource-lifecycle hygiene for any server-held token store handling untrusted-volume input: expired entries must be reclaimed independent of whether they are ever looked up again.
  - Evidence: app/auth.py:92,110-118 — `_tokens` entries are only removed inside reset_password (on success or on-lookup expiry check); a token that is requested and never used again stays in the dict forever, past its own expiry, since nothing ever revisits it.
  - If shipped: Combined with no rate limiting, a long-lived service process accumulates one dict entry per reset request indefinitely, which is an unbounded memory leak under sustained (or abusive) traffic.
