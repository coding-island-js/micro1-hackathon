## What review found

### Raised by the first review, and sent to repair

- **Header column matching is case-sensitive, so common Excel/HR export headers reject the whole file** (high)
  - Requirement: The ticket states files come from 'the customer's own systems — HR exports, spreadsheets, whatever they've got' and the code itself acknowledges header variance by stripping whitespace/BOM; a competent import must tolerate the header-casing variance (`Email`/`EMAIL` vs `email`) that Excel and HR tools routinely produce.
  - Evidence: app/importer.py:50 does `c not in header` with no case-folding. A file with `Email,Name,Team` as the header is verified to produce `Missing required column(s): email, name, team` and zero imported users, even though every required field is present.
  - If shipped: An admin uploads a perfectly good 340-row customer export whose header happens to be capitalized (very common from Excel/Workday/BambooHR exports) and the entire import is rejected with a confusing 'missing column' error, forcing the admin to manually edit the file before every upload.

- **Duplicate column names in the header silently overwrite data instead of being reported as an error** (medium)
  - Requirement: The contract requires 'A row that cannot be imported goes in errors' — a malformed/ambiguous header (two columns with the same name) makes every row's mapping for that column ambiguous and undetectable, which is a file-level defect that must be reported, not silently resolved by last-write-wins.
  - Evidence: app/importer.py:67 does `record = dict(zip(header, row))`. Verified: header `email,name,team,team` with row `ada@example.com,Ada,Eng,Sales` produces `{'team': 'Sales'}` — the 'Eng' value is silently discarded with no error and no indication to the admin that data was lost.
  - If shipped: A customer HR export with a repeated or badly-generated header column (common when exports are hand-edited or merged from multiple systems) causes real field values to vanish without any error message, and the admin has no way to know a user's team/data was dropped.

- **Duplicate emails within the same file are imported as two separate, conflicting user records with no error** (high)
  - Requirement: Email is the natural unique identity key for a user account; a bulk-provisioning import must treat a second row with the same email as an import conflict to report back to the admin, per the same 'rows that can't be imported get reported' contract — this is exactly the kind of dirty data the ticket says these uncontrolled customer exports will contain.
  - Evidence: app/importer.py has no dedup/uniqueness check across rows. Verified: two rows with `ada@example.com` (different name/team) both land in `result.users` with `errors == []`.
  - If shipped: Downstream user creation either throws an unhandled unique-constraint error for the whole batch, or silently creates/overwrites the user with whichever row processes last — the admin gets no warning that the source file had a conflicting duplicate, and account data (team assignment) may end up wrong with no audit trail.

- **The email column is only checked for non-blank, not for valid email syntax** (medium)
  - Requirement: A user-provisioning pipeline consuming an 'email' field must validate it is a syntactically plausible address (RFC 5321/5322 shape) before treating it as an identity/contact channel; the ticket explicitly flags these files as coming from uncontrolled customer systems, i.e. dirty-data is the expected case this feature must guard against.
  - Evidence: app/importer.py:69 only checks `not record[c].strip()` for required columns. Verified: a row with email value `not-an-email` is accepted into `result.users` with no error.
  - If shipped: Garbage or truncated email values from a bad HR export (e.g. a name accidentally shifted into the email column) get provisioned as real accounts; invites/notifications later silently fail to deliver, and the admin only discovers it when users report never receiving onboarding email — well after the import appeared to succeed.
