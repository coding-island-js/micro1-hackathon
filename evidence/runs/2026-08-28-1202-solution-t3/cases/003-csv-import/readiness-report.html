Serious A UTF-8 BOM on the first header cell causes the entire file to be rejected show detail
What happens if you ship it
An admin uploads an Excel-exported HR CSV (the exact scenario the ticket describes) and the entire 340-row import is rejected with a confusing 'missing column' error, even though the columns are clearly present when opened in Excel. Onboarding blocked until someone manually re-saves the file in a different encoding.
The rule it breaks
The importer must handle CSVs 'from the customer's own systems — HR exports, spreadsheets, whatever they've got'; Excel and many Windows tools save CSV as UTF-8-with-BOM by default, and RFC 4180-oriented parsers are expected to strip a leading BOM before parsing the header.
Where in the code
app/importer.py:47 only does column.strip() on header cells, which does not remove '\ufeff'. A file starting with the BOM produces a header cell '\ufeffemail', so 'email' not in header, and import_users returns errors=['missing required column(s): email, ...'] with zero rows imported, even though every row is valid.
Worth fixing Required column matching is case-sensitive, so 'Email'/'Name'/'Team' headers are treated as missing show detail
What happens if you ship it
Any customer export that capitalizes or title-cases its headers (extremely common for HR/spreadsheet exports) is rejected outright with no rows imported, forcing manual CSV editing before every import.
The rule it breaks
Ticket: 'email, name and team must be present' in files that come from arbitrary customer systems whose header casing is not controlled by this team.
Where in the code
app/importer.py:49 checks `column not in header` with exact string equality; a header row of 'Email,Name,Team' fails the required-column check and the whole file is rejected with 'missing required column(s): email, name, team' even though all three columns exist.
Worth fixing A duplicate column name in the header silently overwrites data with no error reported show detail
What happens if you ship it
If a customer's export has a repeated column (common in ad-hoc spreadsheet exports with copy-pasted columns), data for that column is silently lost for every row, and the admin has no way to know an error occurred — result.errors is empty.
The rule it breaks
Ticket: 'Rows that can't be imported get reported back to the admin.' A row whose data is partially discarded due to a malformed header should not be imported silently as if it were fine.
Where in the code
app/importer.py:49 and :66: the required-column check only tests membership ('team' in header), not uniqueness; `dict(zip(header, values))` then collapses duplicate keys, keeping only the last column's value. A header of 'email,name,team,team' with row 'a,B,Eng,Ops' silently produces {'team': 'Ops'} with no error, dropping the first 'team' value entirely and reporting no problem.
Worth fixing Two rows with the same email are both imported as separate users with no dedup or error show detail
What happens if you ship it
Downstream user-creation logic receives two 'new user' records for the same email; depending on how the caller handles it, this either throws an unhandled conflict mid-import (partial import, unclear state) or silently creates/overwrites an account with whichever row processes last — the admin never sees a warning to fix it in the source file.
The rule it breaks
Implicit identity requirement for user provisioning — email is the natural unique key for a user account, so an importer 'adding users' must not hand the caller two conflicting records for the same identity without surfacing that as a data problem.
Where in the code
app/importer.py has no uniqueness check across rows; import_users on 'ada@example.com,Ada,Eng' followed by 'ada@example.com,Ada2,Sales' returns both rows in result.users with errors == [].
Worth fixing Email validation only checks for the presence of '@', accepting clearly malformed addresses show detail
What happens if you ship it
Malformed addresses flow through to account provisioning/invite emails; invite emails silently fail to deliver (bounce) with no error surfaced to the admin during import, and the admin believes the import succeeded cleanly for that user.
The rule it breaks
The importer's own stated behavior — reporting 'invalid email' as a validation error — implies it should catch addresses that cannot be valid, not just ones missing the '@' character entirely.
Where in the code
app/importer.py:77 `if "@" not in record["email"]`. Addresses like 'test@' (no domain), '@nodomain' (no local part), and 'a@b@c' (multiple '@') all pass this check and are imported as valid users.
Minor Reported 'row N' in error messages does not correspond to the physical line in the uploaded file when a quoted field contains an embedded newline show detail
What happens if you ship it
An admin opens the CSV in a text editor/Excel to fix 'row 12' and finds the wrong row for any file containing a quoted newline earlier in the file, making the error report unreliable on real-world exports that include multi-line address/note fields.
The rule it breaks
Ticket: errors are reported 'back to the admin' so the bad rows can be fixed in the source file — this implies the row reference must let the admin locate the actual row.
Where in the code
app/importer.py:56 numbers rows via `enumerate(reader, start=2)`, i.e. by logical CSV record, but a valid quoted multi-line field (e.g. a name containing a newline) consumes more than one physical file line while only counting as one record, so all subsequent 'row N' references are offset from the actual line in the uploaded file.

Serious Malformed CSV input crashes the entire import instead of failing one row show detail
What happens if you ship it
A single stray `\r`-only line ending (common from older HR/spreadsheet export tools) or one oversized free-text field (e.g. a long 'notes' column) anywhere in a 340-row file causes the admin upload view to 500 on the whole request — zero rows import and the admin gets a stack trace instead of a report, even though every other row in the file was fine.
The rule it breaks
Ticket: 'Rows that can't be imported get reported back to the admin, and the rest of the file still imports' — this must hold for any file the customer's own systems can produce, since 'we don't control how they're produced'
Where in the code
app/importer.py wraps nothing around `next(reader)` or the `for row in reader` loop. Python's csv module raises `_csv.Error` for classic-Mac bare-`\r` line endings ('new-line character seen in unquoted field') and for any single field over the default 128KB field_size_limit ('field larger than field limit'). Reproduced: import_users('email,name,team\rada@example.com,...\r') raises _csv.Error uncaught; import_users with one 200KB field also raises _csv.Error uncaught.
Worth fixing Reported error row numbers are wrong when an earlier row has a multi-line quoted field show detail
What happens if you ship it
An admin trying to locate and fix 'row 4' in their spreadsheet/text editor finds the wrong row or no row at all, since any legitimate multi-line field earlier in the file shifts every subsequent reported line number out of sync with the file's actual record order.
The rule it breaks
Ticket: rows that fail must be 'reported back to the admin' — the report is only actionable if it identifies the correct row
Where in the code
app/importer.py:85 uses `reader.line_num`, which counts raw physical text lines, not logical CSV records. Reproduced: with a valid row containing an embedded newline in a quoted field (e.g. a multi-line 'notes' column) followed by a row with a bad email, the error is reported as 'row 4' when the actual data row is the 3rd row in the file (as any spreadsheet app or line-numbered view would count it).
