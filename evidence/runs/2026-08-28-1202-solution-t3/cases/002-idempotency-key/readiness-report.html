Serious Two simultaneous requests with the same idempotency key both reach the processor show detail
What happens if you ship it
The precise bug PAY-208 exists to fix -- a client retry firing while the original request is still in flight (e.g. slow network, not a dropped connection) -- passes the `in` check twice before either write completes, so both requests call `_execute` and the customer is billed twice. This reproduces the double-charge tickets under concurrency instead of eliminating them.
The rule it breaks
Idempotency-Key semantics require mutual exclusion for the duration of processing, not just de-duplication of completed results (RFC draft 'Idempotency-Key HTTP Header Field' and Stripe's documented behavior: a second request received while the first with the same key is still in flight must be rejected or held, not executed).
Where in the code
app/charges.py post_charge (lines 89-102): the guard `if idempotency_key in self._idempotent_results` only checks a dict that is populated *after* `_execute` returns. There is no 'in-progress' marker or lock taken before calling `_execute`. `before_execute` is explicitly documented as the hook Operations uses in staging 'to inject latency and to replay traffic' -- i.e. the exact race this code fails to close.
Serious Reusing a key with different request parameters silently replays the wrong result instead of erroring show detail
What happens if you ship it
A client that reuses a key with a different amount or currency (bug, copy-paste, or key collision) silently gets back the first charge's result -- e.g. told a $50 charge 'succeeded' when only the earlier $25 charge exists, or vice versa. This causes reconciliation mismatches and incorrect confirmations shown to the customer, with no error surfaced to catch the bug.
The rule it breaks
Documented Idempotency-Key behavior (e.g. Stripe API): a key is bound to the exact parameters of the request that first used it; replaying the key with different parameters must return an error (409/422 idempotency-key-mismatch), not the cached response for a different charge.
Where in the code
app/charges.py post_charge: the cache lookup `self._idempotent_results[idempotency_key]` is keyed only by the string key -- `params` is never compared against what was stored for that key on the first call.
Worth fixing Idempotency records have no TTL despite Clock being injected for exactly this purpose show detail
What happens if you ship it
Two production consequences: (1) unbounded memory growth in `_idempotent_results` since nothing is ever purged; (2) a client that legitimately wants to reuse a key after the expected window (e.g. a scheduled job reusing a template key per period) is permanently locked out with a stale replayed result instead of a fresh charge going through.
The rule it breaks
Published idempotency-key behavior scopes keys to a bounded window (e.g. 24 hours in Stripe's implementation) after which the same key may legitimately start a new operation; keys must not be retained forever.
Where in the code
app/charges.py: `Clock.now()` is only ever read inside the provided `_execute` for the ledger timestamp. `post_charge` never calls `self.clock.now()`, so `_idempotent_results` entries carry no timestamp and are never evicted or expired.
Minor Idempotency key is accepted with no format/type/length validation show detail
What happens if you ship it
If any caller ever sends an empty idempotency key by mistake (e.g. a header default of `""` instead of absent), every such request collides on the same cache slot and unrelated charges silently return each other's cached results. A malformed key type crashes the endpoint with a 500 instead of a clean validation error.
The rule it breaks
API input-boundary handling: values used as a cross-request correlation/lookup key must be validated (non-empty, bounded length, expected type) before being trusted, per standard API hardening practice for idempotency headers.
Where in the code
app/charges.py post_charge: the only check is `idempotency_key is not None`. An empty string `""` is accepted as a valid, distinct key; a non-hashable type passed as `idempotency_key` (e.g. a list, if a caller's header-parsing layer misbehaves) would raise an unhandled `TypeError` from the dict lookup rather than returning a controlled 400.

Serious A dropped connection/exception during _execute() leaves the idempotency key unrecorded, so the retry re-charges show detail
What happens if you ship it
Reproduced directly: a first call that appends to self.executed (processor contacted) and then raises produces a second, distinct entry in self.executed on retry with the identical idempotency key — a genuine double charge, which is precisely the bug PAY-208 was filed to eliminate.
The rule it breaks
The ticket's core requirement: 'if we see the same key again we shouldn't put a second charge through', specifically for the case of a dropped client connection followed by a retry
Where in the code
app/charges.py:159-165 — self._execute(params) is called and, only if it returns normally, the result is stored in self._idempotent_results. If _execute (or before_execute, which Operations monkey-patches to inject latency/replay traffic) raises or the process is killed/times out mid-call — the exact 'connection drops' scenario in the ticket — the code jumps straight past the record-write and the per-key lock is released via the `with` block having recorded nothing.
Serious A transient upstream 5xx is cached under the idempotency key for the full 24h TTL, blocking all legitimate retries show detail
What happens if you ship it
A customer whose card was never actually charged (processor down) cannot complete the payment for up to a day unless the client fabricates a brand-new idempotency key — which reintroduces the double-charge risk the feature exists to prevent, since the client can't safely know whether the original attempt actually succeeded downstream.
The rule it breaks
Idempotency layers (this ticket cites the Stripe 24h window as the model) must let a client recover from a transient processor/network failure by retrying — they must not turn a temporary outage into a guaranteed failure for the entire key lifetime.
Where in the code
app/charges.py:159-164 stores the _execute() result unconditionally, including a 500 'processor unavailable' response, into self._idempotent_results with a fresh 24h expiry. Reproduced: after one 500 response, an identical retry with the same key returns the exact same cached 500 (same ref) instead of re-attempting the charge, for up to 24 hours.
Serious Idempotency records and locks live only in one process's memory, not a shared/persistent store show detail
What happens if you ship it
A mobile client's automatic retry (the ticket's stated trigger) that lands on a different worker process, or arrives after a deploy/restart, will find no record of the key and will be charged again — the exact double-charge failure mode from the support tickets, un-fixed for any multi-instance deployment.
The rule it breaks
For a retry to be caught, the second attempt must be visible to whichever instance handles it. A payments API deployed with multiple workers/processes/pods (the normal topology for a P1 payments endpoint) must share idempotency state across instances and survive restarts/deploys.
Where in the code
app/charges.py:74-80 — self._idempotent_results and self._key_locks are plain in-memory dicts on the ChargeAPI instance, with no persistence or cross-process coordination (e.g. a database unique constraint or shared cache).
Worth fixing _purge_expired mutates the shared results dict under only a per-key lock, not a lock guarding the dict itself show detail
What happens if you ship it
Under concurrent traffic with expiring keys, this can corrupt dict state or raise a runtime error during iteration/deletion, taking down in-flight charge requests for unrelated keys.
The rule it breaks
Concurrent requests using different idempotency keys must not corrupt shared idempotency state ('two attempts at once' safety, which the per-key lock design otherwise aims for).
Where in the code
app/charges.py:122-126 — _purge_expired() iterates and deletes from self._idempotent_results while holding only the lock for the current request's key (charges.py:143). Two threads processing two different keys can call _purge_expired concurrently and mutate the same dict with no shared lock protecting it.
Minor Every distinct idempotency key ever seen keeps a Lock object forever, even after its result record is purged show detail
What happens if you ship it
self._key_locks grows without bound for the lifetime of the process, since real traffic uses a fresh idempotency key per charge attempt — steady memory growth that eventually leads to increased memory pressure/OOM on a long-lived instance.
The rule it breaks
State that outlives a single call must be bounded; a long-running payments service processing a high volume of unique idempotency keys cannot hold unbounded per-key state.
Where in the code
app/charges.py:111-117, _key_lock() adds an entry to self._key_locks for every new key and nothing ever removes entries from that dict, even though _purge_expired (charges.py:122-126) removes the corresponding entry from self._idempotent_results.
