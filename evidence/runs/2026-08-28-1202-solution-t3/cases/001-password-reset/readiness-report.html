What the review found

Raised by the first pass and sent to the repair step.

high

Old reset tokens remain valid after a new request or a successful reset

The rule it breaks
OWASP Forgot Password Cheat Sheet: issuing a new reset token should invalidate previously issued ones, and a successful password change must invalidate all other outstanding reset tokens for that account.
Where
app/auth.py request_reset() keys self._tokens by token, not by email, and never removes other entries for the same email; reset_password() only deletes the single token it was called with (lines 94-127).
If you ship it
If a user requests a reset twice (e.g. clicks 'resend'), or an attacker has an old reset email from a compromised mailbox, that old token is still live for up to an hour after the user has already reset their password with a newer link — a valid path to account takeover using a stale token the user believed was dead.
high

reset_password accepts empty or trivially weak passwords

The rule it breaks
NIST SP 800-63B / standard password-reset practice: a minimum length (>=8 chars) and non-empty check must be enforced when a new credential is set.
Where
app/auth.py reset_password() calls hash_password(new_password) with no validation on new_password at all (line 125).
If you ship it
A caller can reset an account's password to the empty string; verify_password('', hash) then succeeds, leaving the account effectively unprotected. A security reviewer would block this feature on this alone.
high

Two simultaneous reset_password calls with the same token race and can crash or silently overwrite each other

The rule it breaks
Single-use token semantics require the check-and-consume of a token to be atomic; concurrent redemption of the same token must not both succeed or corrupt state.
Where
app/auth.py reset_password(): entry = self._tokens.get(token) is read, then several statements later del self._tokens[token] removes it, with no lock around the sequence (lines 111-127).
If you ship it
Under a threaded server, two near-simultaneous requests (double-click, client retry after timeout) can both pass the 'entry is None' check before either deletes the token: both overwrite password_hash (last write wins, non-deterministic which password survives) and the second del raises an uncaught KeyError, surfacing as a 500 to one of the requests while the password was already changed underneath the user.
low

Expired, unused tokens are never purged from memory

The rule it breaks
Bounded resource usage for stateful, per-request server data — expired credentials/tokens should be reaped, not retained indefinitely.
Where
app/auth.py: self._tokens entries are only removed inside reset_password() (on success, on found-but-expired, or on missing user); a token nobody ever redeems sits in the dict forever since request_reset() never sweeps expired entries.
If you ship it
In a long-running process handling routine forgot-password traffic, the in-memory token map grows without bound (most users never click a stale link), leading to unbounded memory growth over the service's uptime.
medium

request_reset has no rate limit, enabling email-bombing of a victim

The rule it breaks
Self-service password reset endpoints must be throttled per account/IP to prevent abuse of the outbound-email side effect (OWASP ASVS 2.10 / abuse-of-functionality controls).
Where
app/auth.py request_reset() performs no throttling — any caller can invoke it repeatedly for the same email, each call generates a token and calls mailer.send() (lines 94-108).
If you ship it
An attacker can script repeated calls to flood a victim's inbox with reset emails (harassment/DoS), and each call also adds another still-valid token to the store, compounding the stale-token issue above.
medium

request_reset does materially different work for known vs unknown emails, despite the code's own anti-enumeration intent

The rule it breaks
Anti user-enumeration requirement stated directly in the code's own comment ('Don't reveal whether an email is registered') — this requires the response and its timing to be indistinguishable for registered vs unregistered addresses.
Where
app/auth.py request_reset(): unknown emails return immediately (line 95-97); known emails additionally generate a token, write to the dict, and call mailer.send (lines 99-108) — asymmetric work.
If you ship it
In production, Mailer.send would involve real network I/O (SMTP/API call) taking milliseconds-to-seconds, versus a near-instant return for unknown emails — a measurable timing oracle an attacker can use to enumerate registered accounts, defeating the stated goal.

medium

request_reset does asymmetric work for existing vs. non-existing accounts, defeating its own anti-enumeration goal

The rule it breaks
OWASP Forgot Password Cheat Sheet: the response to a reset request must be indistinguishable (including timing) for registered and unregistered emails, which is exactly what the code's own comment claims to guarantee ('Do the same work whether or not the email is registered').
Where
app/auth.py request_reset(): for a known user it additionally runs _invalidate_tokens_for_email_locked, allocates dict/set entries and stores the token (self._tokens[token]=..., self._tokens_by_email.setdefault...); for an unknown user this entire branch is skipped. Only new_token() and mailer.send() are common to both paths.
If you ship it
An attacker who can measure response latency (even coarsely, with repeated sampling) can distinguish registered from unregistered emails, enabling account enumeration -- the precise attack the code comment says it prevents.
high

Reset tokens and cooldown state live only in local process memory with no injection point, unlike the user store

The rule it breaks
A self-service password reset flow must work correctly in a horizontally-scaled, restart-tolerant production deployment (the standard operating model implied by 'account service') -- a token issued by the instance that handled request_reset must be redeemable by whichever instance handles the follow-up reset_password call.
Where
app/auth.py PasswordResetService.__init__ hardcodes self._tokens/_tokens_by_email/_last_request_at as plain in-process dicts; unlike `users` (passed in as 'the live user store'), there is no way to back these with a shared/persistent store.
If you ship it
In any multi-instance or auto-restarting deployment, a user who requests a reset on one instance and clicks the link routed to another instance (or after a deploy/restart) gets a false 'invalid token' -- the exact support burden ('email us and we reset it by hand') this ticket was meant to eliminate.
medium

Only a per-email 60s cooldown exists; there is no per-IP or global throttle, and the service happily emails unregistered/arbitrary addresses

The rule it breaks
OWASP Forgot Password Cheat Sheet velocity-checking guidance: reset-request endpoints must be protected by IP/account-independent rate limiting, not just per-account throttling, because the endpoint sends mail to attacker-chosen addresses regardless of whether they belong to a real account.
Where
app/auth.py request_reset(): throttling is keyed solely on `email` via self._last_request_at; mailer.send(to=email, ...) is invoked even when self.users.get(email) is None, with no IP or caller-identity throttle anywhere in the class.
If you ship it
An attacker can iterate arbitrary third-party email addresses (one request per address, unlimited addresses) to use the account service as a spam/email-bombing relay, since each distinct address only needs to be hit once per 60 seconds and there is no ceiling on distinct addresses per requester.
low

No confirmation/notification email is sent to the account owner after a successful password reset

The rule it breaks
OWASP Forgot Password Cheat Sheet 'Notify User of Password Reset': the account owner must be informed out-of-band when their password is changed, so an attacker-initiated reset (e.g. via a leaked or intercepted token) is detectable.
Where
app/auth.py reset_password(): on success it sets user.password_hash and invalidates outstanding tokens, but never calls self.mailer.send with a change-notification message.
If you ship it
If an attacker manages to obtain and redeem a valid reset token (e.g. via a compromised mailbox or shared/forwarded link), the legitimate owner receives no signal that their password was just changed, delaying detection of account takeover.
