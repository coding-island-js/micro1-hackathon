## What review found

### Raised by the first review, and sent to repair

- **Older, unused reset tokens remain valid after a newer one is issued or used** (high)
  - Requirement: OWASP Forgot Password Cheat Sheet: a password reset token must be single-use, and issuing a new reset token (or successfully using one) must invalidate any other outstanding tokens for that account — otherwise multiple valid 'keys' to the same account coexist.
  - Evidence: app/auth.py request_reset() always adds a new entry to self._resets without removing prior entries for the same email (lines 99-101); reset_password() only deletes the single token that was used (line 126), leaving sibling tokens for the same account fully valid until their own TTL expires.
  - If shipped: If a user requests a reset twice (e.g. clicks 'resend'), or if an old reset email is leaked/cached/forwarded, an attacker holding any previously issued token can still take over the account even after the legitimate user has already reset their password with a different token. This defeats the purpose of a reset link being a one-time credential.

- **Token is treated as still valid at the exact moment it expires** (low)
  - Requirement: Standard token-expiry semantics (cf. RFC 7519 §4.1.4 exp claim: 'the current date/time MUST be before the expiration date/time'). A token whose TTL has fully elapsed (now == expires_at) should be rejected, not accepted.
  - Evidence: app/auth.py reset_password() uses `if self.clock.now() > expires_at:` (line 116), a strict greater-than, so when clock.now() == expires_at (i.e. exactly TOKEN_TTL_SECONDS after issuance) the token is still accepted.
  - If shipped: A token issued at t0 with a 30-minute TTL is usable at exactly t0+1800s, one tick past its advertised lifetime, in violation of the TTL guarantee the security/compliance reviewer would expect ('expires after 30 minutes' means unusable at or after that mark, not one second later).


### Still flagged after the repair pass

- **Requesting a new reset link does not invalidate previously issued, still-unexpired tokens for the same user** (high)
  - Requirement: OWASP Forgot Password Cheat Sheet: when a new reset token is issued, any previously issued outstanding token for that account must be invalidated so only the most recently sent link is usable
  - Evidence: app/auth.py request_reset() (lines 94-108) inserts a new (token -> email, expiry) entry into self._resets without removing or expiring any other live entries for the same email. reset_password() only purges other tokens for that email *after* a successful reset (lines 127-129), not when a new request is issued.
  - If shipped: If a user (or an attacker triggering repeated 'forgot password' requests) generates several reset emails, every one of them stays valid for the full 30-minute TTL. An old email sitting in an inbox, a forwarded message, or a link cached by a mail scanner/proxy can be used to take over the account even after the user requested — and believes they are using — a fresher link. This is exactly the multiple-valid-token scenario the OWASP cheat sheet calls out as unacceptable and a payments/security reviewer would block on.

- **Repeated reset requests accumulate unbounded state in the in-memory token store with no cap or cleanup** (medium)
  - Requirement: A service-issued, time-bounded credential store must not allow a single actor to grow server-held state without bound (resource-exhaustion / availability requirement any security reviewer applies to token stores)
  - Evidence: app/auth.py request_reset() unconditionally adds a new entry to self._resets on every call (line 101) and never caps or evicts entries for a given email; expired entries are only pruned lazily, and only if someone later calls reset_password() with that exact expired token (lines 116-118). Entries that are never redeemed or retried are never removed.
  - If shipped: Because request_reset() is the pre-authentication, 'don't reveal if the email exists' endpoint, an unauthenticated caller can invoke it against a known or guessed valid email arbitrarily many times, each call permanently growing the service's in-memory _resets dict for up to the full TTL (and forever if never cleaned). At scale this is a straightforward unauthenticated memory-exhaustion vector against the account service.
