## What review found

### Raised by the first review, and sent to repair

- **No locking around the idempotency cache lets two simultaneous requests with the same key both execute the charge** (high)
  - Requirement: Idempotency-Key semantics (Stripe API / IETF draft-ietf-httpapi-idempotency-key-header): a second request with the same key that arrives while the first is still in flight must not be allowed to independently reach the processor — it must wait for or be rejected in favor of the in-flight attempt.
  - Evidence: app/charges.py:89-102 — post_charge does `if key in cache: return cache[key]` and only writes to `self._idempotency_cache` *after* `_execute` returns. Between the read and the write there is no lock, so two threads (or two concurrent request handlers) both see a cache miss and both call `self._execute(params)`, each appending its own attempt to `self.executed`.
  - If shipped: This is exactly the scenario the ticket exists to fix: 'the client's connection drops, it retries the charge.' A dropped connection frequently means the client gave up waiting while the original request was still being processed server-side — so the retry arrives concurrently with, not after, the first attempt. The current fix only protects sequential retries and leaves the concurrent case — arguably the more common one for a mobile SDK's automatic retry — fully exposed to double-charging.

- **Reusing an idempotency key with a different request payload silently replays the first request's response instead of flagging a conflict** (medium)
  - Requirement: Idempotency-Key spec convention (Stripe docs, IETF idempotency-key-header draft): if an idempotency key is reused with parameters that differ from the original request, the server must reject the request (typically 409/422) rather than replaying a cached response for an unrelated payload.
  - Evidence: app/charges.py:90-91 — the cache lookup keys only on `idempotency_key` and ignores `params` entirely, so `post_charge({"amount": 9900, ...}, idempotency_key="k1")` after an earlier call with amount 2500 and the same key returns the cached 2500 response verbatim, with no comparison of the incoming params to what was originally stored.
  - If shipped: If a client ever reuses a key across two logically different charges (a bug in client-side key generation, a stale key cached in a mobile app, a different cart amount retried under an old key), the caller receives a '200 succeeded' response describing a charge that was never made for the new amount — while believing the new amount was billed. Order/fulfillment systems that trust this response can ship goods or grant entitlements the customer was never actually charged for, and reconciliation between the charge ledger and order records will silently diverge.

- **Idempotency cache entries are kept forever with no TTL/eviction** (low)
  - Requirement: Idempotency-Key spec convention (Stripe: keys expire after 24 hours): stored idempotency records must have a bounded lifetime so memory is reclaimed and keys can eventually be reused for new operations.
  - Evidence: app/charges.py:58,99-100 — `self._idempotency_cache` is a plain dict that entries are only ever added to, never removed or expired, despite the class being handed a `Clock` (whose docstring flags it as 'the service's only source of time') that post_charge never actually calls.
  - If shipped: In a long-lived process handling many unique idempotency keys, the cache grows without bound, which is a slow memory leak; separately, since there's no expiry, a key can never be legitimately reused even after the original transaction is long settled, which may surprise integrators relying on standard (e.g. Stripe-like) 24-hour expiry semantics.


### Still flagged after the repair pass

- **Losing (waiting) requests call before_execute() directly, outside of _execute, duplicating the processor-contact hook per logical charge** (medium)
  - Requirement: Provided contract: 'before_execute ... called at the moment the charge starts ... _execute calls it for you -- just don't remove the call to _execute.' before_execute is documented as being invoked exactly once per actual attempt on the processor (Operations uses it in staging to inject latency and replay traffic), not once per HTTP request that merely observes an in-flight attempt.
  - Evidence: app/charges.py:126-131 -- in the 'is_owner is False' branch, post_charge calls `self.before_execute()` directly (not via `_execute`) before blocking on `with key_lock: pass`. This runs before_execute a second time for the same logical charge, even though only the owner thread actually reaches `_execute`/the processor.
  - If shipped: In staging, where before_execute is monkey-patched to inject latency or replay traffic against a real/simulated processor, every concurrent duplicate request (e.g. a mobile client's automatic retry that arrives while the first attempt is still in flight) triggers an extra, spurious invocation of that hook that is not tied to any real attempt in `self.executed`. This can trigger extra replayed traffic or latency injection per concurrent retry, corrupting replay/staging test results, and is a hook invoked outside its documented single-call-per-attempt contract.

- **A 500 (processor unavailable / ambiguous outcome) response is cached forever under the idempotency key, so a legitimate client retry can never actually reach the processor again** (high)
  - Requirement: Documented idempotency-key behaviour for payment APIs this feature imitates (e.g. Stripe's Idempotent Requests): responses are only cached and replayed once the processor gave a definitive answer; a 500-level / ambiguous outcome must not be treated as final, so retries with the same key are allowed to actually re-attempt against the processor.
  - Evidence: app/charges.py:113-124 -- the owner branch caches `result` from `_execute(params)` in `_idempotency_cache` regardless of status code, including 500 responses from `params.get('simulate') == 'processor_down'`. Any subsequent request with the same key returns the cached 500 forever (line 108) instead of calling `_execute` again.
  - If shipped: If the upstream processor is transiently unavailable (a real 500, not a validation error), the client's automatic retry -- the exact scenario this ticket exists to fix -- is permanently stuck replaying the same cached failure and can never successfully complete the charge with that key, even after the processor recovers. The customer's payment is silently blocked with no path to success short of generating a brand-new idempotency key (which reintroduces the double-charge risk PAY-208 was meant to eliminate, since the ambiguous first attempt's ultimate fate is unknown).

- **Idempotency keys and their cached results/locks are retained forever with no TTL, so keys can never be reused and both cache dicts grow without bound** (medium)
  - Requirement: Standard idempotency-key semantics (Stripe's 'Idempotent Requests', the IETF draft-ietf-httpapi-idempotency-key-header) define a bounded retention window (e.g. 24 hours) after which a key expires and becomes available for reuse; production services must also bound state that scales with request volume.
  - Evidence: app/charges.py:56-61,99-124 -- `_idempotency_cache` and `_key_locks` are plain dicts with no expiry/eviction logic anywhere, and `self.clock` is only ever read at charges.py:83 to stamp the `at` field of an attempt -- it is never consulted to expire cache entries. The `Clock` the ticket instructs to use for all time decisions is unused for the idempotency feature itself.
  - If shipped: Every unique idempotency key a client ever sends is retained for the lifetime of the process: (1) memory grows unboundedly as request volume grows, a resource-exhaustion risk for a long-running payments service; (2) a client that legitimately wants to reuse a key value after a reasonable window (per documented processor behaviour) for a new, unrelated charge is permanently met with a 409 conflict instead of a fresh charge.
