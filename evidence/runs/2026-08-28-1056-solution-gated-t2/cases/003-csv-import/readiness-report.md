## What review found

### Raised by the first review, and sent to repair

- **UTF-8 BOM on the first header cell causes the whole file to be rejected** (high)
  - Requirement: Files come from the customer's own systems (HR exports, spreadsheets) which the ticket explicitly says we don't control the production of; Excel's 'CSV UTF-8' export — one of the most common ways non-technical admins produce a CSV — prepends a U+FEFF byte-order-mark to the file, which becomes part of the first header cell unless decoded with utf-8-sig.
  - Evidence: app/importer.py:45 does `header = [col.strip() for col in rows[0]]`, and `.strip()` does not remove `\ufeff`. So a file starting with a BOM has its first header cell become `'\ufeffemail'` instead of `'email'`, which fails the `col not in header` check at line 46 for every required column that happens to be first, rejecting the entire file with 'Missing required column(s)' even though every row is well-formed.
  - If shipped: An admin uploads a perfectly valid Excel-exported CSV (the exact scenario the ticket describes) and gets zero users imported and a baffling 'missing email/name/team column' error, even though the file visibly has those columns. Onboarding is blocked with no actionable fix visible to the admin.

- **Duplicate header column names silently discard data instead of being reported** (medium)
  - Requirement: Ticket: 'Rows that can't be imported get reported back to the admin' — a row whose data is silently overwritten/discarded due to an ambiguous header should be reported, not passed through with data quietly dropped and no error raised.
  - Evidence: app/importer.py:63 builds `record = dict(zip(header, row))`. If the header contains a repeated column name (e.g. a malformed HR export with two 'email' columns), `dict(...)` keeps only the last value for that key, silently losing the first column's value with no entry in `result.errors` and no indication in `result.users` that data was dropped.
  - If shipped: A customer's export with a duplicated/misaligned header (not unheard of in ad-hoc spreadsheet exports) causes real user data to vanish without any error surfacing to the admin, who believes the import succeeded cleanly for that row.


### Still flagged after the repair pass

- **A single oversized CSV field raises an unhandled exception and kills the entire import** (high)
  - Requirement: Ticket: 'Rows that can't be imported get reported back to the admin, and the rest of the file still imports.' Also: files come from customer systems ('HR exports, spreadsheets, whatever they've got — so we don't control how they're produced'), so parsing must tolerate malformed/oversized input rather than crash.
  - Evidence: app/importer.py:43 calls `list(csv.reader(StringIO(csv_text)))` eagerly, with no try/except. Python's csv module enforces a field size limit (131072 bytes by default) and raises `_csv.Error: field larger than field limit` when exceeded. Since this happens while materializing `rows`, it happens before any row is even parsed, and propagates straight out of `import_users` as an uncaught exception.
  - If shipped: Any customer file with one abnormally large cell (a pasted document, a huge notes/description column, a corrupted export) crashes the whole admin upload request with a 500 instead of reporting that one row as an error and importing the other 339 good rows. This directly contradicts the 'rest of the file still imports' guarantee and turns a single bad row into a total onboarding failure.

- **Required column check is case-sensitive, so real-world exports with Title-Case headers are rejected entirely** (medium)
  - Requirement: Ticket: 'email, name and team must be present' in the header, combined with 'The files come from the customer's own systems — HR exports, spreadsheets, whatever they've got — so we don't control how they're produced.' A file whose header reads Email/Name/Team (extremely common from Excel/HR exports) does in fact name those columns, but the importer rejects the whole file.
  - Evidence: app/importer.py:48-54: `header = [col.strip() for col in rows[0]]` only strips whitespace, then `missing_columns = [col for col in REQUIRED_COLUMNS if col not in header]` does an exact case-sensitive string comparison against lowercase REQUIRED_COLUMNS. A header of `Email,Name,Team` fails this check and every row is rejected with 'Missing required column(s): email, name, team' even though the data is otherwise complete.
  - If shipped: An admin uploads a perfectly normal HR export with capitalized column headers and gets a hard 'missing required column' error with zero users imported, even though every required column is present under a different case. They have no way to fix this except manually editing the CSV, defeating the purpose of the bulk-import feature for the very files it was built to accept.

- **Leading/trailing whitespace on required field values is checked for emptiness but not stripped from the stored record** (medium)
  - Requirement: Internal consistency of the code's own validation: `missing_values` is computed via `record.get(col, '').strip()`, i.e. the code itself treats whitespace as insignificant when deciding if a required value is present — but then stores the untrimmed raw value in `result.users`, so the same whitespace it just decided doesn't count as content is preserved in the output used to create the account.
  - Evidence: app/importer.py:73-83: `record = dict(zip(header, row))` keeps raw values; the presence check strips before testing but the stored dict is never normalized, so `' ada@example.com '` passes validation and lands in `result.users[0]['email']` with the surrounding spaces intact.
  - If shipped: Emails/names pulled from spreadsheet cells with accidental padding (very common from copy-paste HR exports) get created as user accounts with leading/trailing whitespace baked into the email address, which is likely to break email-uniqueness checks, login matching, or downstream validation that expects a clean address — and produces near-duplicate accounts that differ only by invisible whitespace.
