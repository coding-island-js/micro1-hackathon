## What review found

### Raised by the first review, and sent to repair

- **Idempotency key is not reserved before the charge executes, so concurrent retries with the same key both charge** (high)
  - Requirement: The core purpose of an idempotency key (as documented for this pattern, e.g. Stripe's Idempotency-Key) is that a second request with the same key while the first is still in flight must not be allowed to execute a second charge -- it must block/409 or wait, not double-execute. This is exactly the double-charge scenario in the ticket ('connection drops, client retries').
  - Evidence: app/charges.py:89-102 -- post_charge only checks `if idempotency_key in self._idempotency_store` (a dict lookup against completed results) and only writes to the store *after* `_execute` returns. There is no placeholder/lock inserted at the start of the call. Two near-simultaneous calls with the same key both miss the store, both reach `self._execute(params)`, and both append to `self.executed`.
  - If shipped: The mobile SDK's automatic retry -- the exact trigger described in the ticket -- fires a second request before the first response (or its store write) has landed, e.g. because the first call is slow inside `_execute`/`before_execute` (staging even injects latency there). Both calls execute and the customer is charged twice, which is the precise bug PAY-208 was opened to fix.

- **Reusing a key with different request parameters silently returns the first charge's result instead of erroring** (high)
  - Requirement: Idempotency-key semantics require the server to store the request fingerprint (params) alongside the cached response, and reject key reuse with mismatched parameters (Stripe returns 400/422 'Keys for idempotent requests can only be used with the same parameters as the original request'). A key must not be a bare cache of 'whatever happened last time this string appeared'.
  - Evidence: app/charges.py:58,90-100 -- `_idempotency_store` maps key -> (status, body) only; the original `params` are never stored or compared. `post_charge` returns the cached tuple regardless of what `params` the second call carries.
  - If shipped: A client bug or key-space collision that reuses a key for a different amount/currency gets back a 200 with the wrong amount and no error, silently misleading both client and customer about what was actually charged -- and hides the client-side bug that caused key reuse in the first place.

- **Idempotency records are kept forever in process memory with no TTL, despite being told to use the injected Clock** (medium)
  - Requirement: Documented idempotency-key behavior (Stripe: keys expire after 24 hours) requires bounded retention tied to time, both to cap storage growth and to define how long a client's retry window is protected. The ticket explicitly says 'Take time from the injected Clock, never time.time()', signalling that time-based expiry was part of the intended design.
  - Evidence: app/charges.py:58,89-102 -- `_idempotency_store` is a plain dict with no eviction, and `self.clock` is never referenced in `post_charge` (only read inside the provided `_execute` for the `at` timestamp).
  - If shipped: In a long-running process, the store grows without bound (memory leak / unbounded resource use for a payments service), and there is no way to reason about or test what should happen when a key is reused after a legitimate, much later, distinct charge attempt -- the current code will treat a key from a year-old charge as still valid forever.

- **Idempotency state lives only in one ChargeAPI instance's memory and is lost on restart or when a retry lands on a different process** (high)
  - Requirement: For a payments endpoint behind multiple workers/instances (the normal deployment shape this ticket is meant to fix double-charges for), the idempotency ledger must be durable/shared (e.g. a database or distributed cache) so that any instance handling the retry sees the same record.
  - Evidence: app/charges.py:58 -- `self._idempotency_store` is a plain in-process dict, scoped to the `ChargeAPI` instance with no persistence.
  - If shipped: The mobile SDK's retry (the ticket's stated cause of double charges) is likely to hit a different process/pod, or the same process after a crash/redeploy, than the one that handled the original attempt; that retry finds no record of the key and charges again -- the exact failure mode PAY-208 exists to eliminate.
