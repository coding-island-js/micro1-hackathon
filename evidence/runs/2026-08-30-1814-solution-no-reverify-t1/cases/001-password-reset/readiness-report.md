## What review found

### Raised by the first review, and sent to repair

- **Requesting a new reset link does not invalidate previously issued tokens** (high)
  - Requirement: OWASP Forgot Password Cheat Sheet: a new password reset request should invalidate any previously issued reset token for that account, so only the most recently issued token is usable
  - Evidence: app/auth.py:94-107 `request_reset` always mints a fresh token and adds it to `self._tokens` but never removes or invalidates any prior token already outstanding for the same email. Verified empirically: after calling `request_reset('ada@example.com')` twice, the first token (t1) was still accepted by `reset_password` and successfully changed the password.
  - If shipped: If an older reset email is exposed (forwarded, cached, left in an old inbox, intercepted, or the user re-requested because they thought the first email was compromised/expired), that older link keeps working for a full hour regardless of how many newer resets were requested. An attacker who obtains any historical reset email can still take over the account even after the legitimate user 'refreshed' their request.

- **request_reset has no throttling, enabling email-bombing and enumeration probing** (medium)
  - Requirement: OWASP Forgot Password Cheat Sheet / ASVS 2.5: forgot-password endpoints must be rate-limited per account and per source to prevent abuse (mail-bombing a victim's inbox) and to slow account-enumeration attempts
  - Evidence: app/auth.py:94-107 — `request_reset` performs no frequency check; it will happily send an unlimited number of emails for the same address as fast as it's called.
  - If shipped: An attacker can call `request_reset` in a loop to flood a victim's inbox with reset emails (harassment / phishing cover) or hammer the endpoint to farm timing/enumeration signals, with no built-in defense.

- **Response behavior for unknown vs known email differs observably** (medium)
  - Requirement: OWASP Forgot Password Cheat Sheet: 'the response ... should be identical regardless of whether the account exists' (wording, timing, and side effects) to prevent user enumeration
  - Evidence: app/auth.py:95-96 short-circuits with `return` immediately for an unknown email, doing none of the token generation, dict write, or `mailer.send` work that the known-email path performs (lines 98-107).
  - If shipped: The measurable difference in work done (and therefore latency, plus the absence of any queued mail) lets an attacker distinguish registered from unregistered email addresses, enabling account enumeration for follow-on credential attacks.

- **Expired/unused tokens are never purged except lazily on redemption** (medium)
  - Requirement: Sound lifecycle management for security tokens: expired credentials must be reaped so storage doesn't grow without bound (implicit requirement given TOKEN_TTL_SECONDS exists at all)
  - Evidence: app/auth.py:92,99-100 — `self._tokens[token] = (email, expires_at)` is only ever removed inside `reset_password` (lines 116, 119), i.e. only if someone actually presents that exact token. There is no background sweep and no cap.
  - If shipped: Combined with the lack of rate limiting, every `request_reset` call permanently grows `_tokens` for the life of the process if the resulting email is never clicked, giving an unauthenticated caller an easy unbounded-memory-growth vector (DoS) against the account service.

- **Email lookup for reset requests is case-sensitive, unlike normal login** (medium)
  - Requirement: RFC 5321 treats the domain part of an email address as case-insensitive, and virtually all real-world auth systems (and this ticket's own `users` store, keyed however accounts were created) must be reachable regardless of the case a user types when self-servicing a reset — otherwise the very support burden the ticket exists to reduce simply moves to 'my reset link never arrived'
  - Evidence: app/auth.py:95 `if email not in self.users: return` does an exact-string dict lookup with no normalization. Verified: `request_reset('Ada@Example.com')` against a user stored as `ada@example.com` silently sends zero emails.
  - If shipped: A legitimate user who types their email with different casing than however it was originally stored gets no error and no email, and has no way to know whether the request 'worked' — they fall back to emailing support, which is exactly the load ACCT-412 was meant to eliminate.

- **reset_password accepts an empty or arbitrarily weak new password** (medium)
  - Requirement: NIST SP 800-63B §5.1.1.2 requires verifiers to enforce a minimum length (8 characters) on user-chosen passwords; this is the only code path in the service that sets a raw new password, so it is the enforcement point
  - Evidence: app/auth.py:109-121 — `reset_password` passes `new_password` straight to `hash_password` with no length or content check. Verified empirically: `reset_password(token, '')` returns True and leaves the account with an empty-string password.
  - If shipped: A user (or an attacker who obtains a valid token) can set the account password to an empty string or a single character, leaving the account trivially guessable through the normal login path going forward.

- **No synchronization guarding the check-then-delete on the shared token store** (low)
  - Requirement: Single-use token requirement (OWASP Forgot Password Cheat Sheet: reset tokens must be usable exactly once) implies redemption must be atomic against concurrent redemption attempts
  - Evidence: app/auth.py:110-121 — `reset_password` does `entry = self._tokens.get(token)`, then a TTL comparison, then `del self._tokens[token]`, then mutates `self.users[email]`, as separate, unlocked statements on a plain dict.
  - If shipped: If the service is served by multiple threads sharing one `PasswordResetService` instance (a normal deployment for a web app), two simultaneous submissions of the same token can both pass the `entry is None`/expiry checks before either deletes it, letting the token be 'used' twice (e.g. two different password values racing to win) instead of enforcing strict single-use semantics.
