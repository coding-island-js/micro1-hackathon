## What review found

### Raised by the first review, and sent to repair

- **UTF-8 BOM in header causes valid spreadsheet exports to be rejected entirely** (high)
  - Requirement: RFC 4180 does not forbid a BOM, and Microsoft Excel's 'CSV UTF-8' export (a primary source explicitly named in the ticket: 'HR exports, spreadsheets, whatever they've got') prepends a BOM (U+FEFF) to the first field by default. A conforming importer of arbitrary third-party CSVs must strip or tolerate a leading BOM.
  - Evidence: app/importer.py strips whitespace from header cells (`column.strip()`) but never strips U+FEFF. A file with a BOM produces a header of ['\ufeffemail', 'name', 'team'], so `'email' not in header` is true and the whole file is rejected with 'missing required column(s): email' even though every row is otherwise valid.
  - If shipped: An admin exports a CSV UTF-8 file from Excel (the most common way non-technical HR staff produce CSVs on Windows) and the entire 340-row import is rejected with a confusing 'missing email column' error, even though the column is clearly there when they open the file. They have no way to fix this without knowing what a BOM is.

- **Duplicate column names in the header silently overwrite data with no error** (high)
  - Requirement: The ticket requires that a row that cannot be imported be reported in `errors`, and that data be carried through 'as-is'. Silently discarding a column's data because of a header collision violates both: the row is imported but not faithfully, and no error is reported for the data loss.
  - Evidence: app/importer.py:78 builds `record = dict(zip(header, row))`. If the header has a repeated name (e.g. two columns both named 'name', or a customer export with a duplicated 'email' column), the later column silently overwrites the earlier one in the dict, with zero errors surfaced. Verified: `email,name,team,name` with data `...,Nickname` produces `users[0]['name'] == 'Nickname'`, silently discarding 'Ada Lovelace'.
  - If shipped: A malformed customer export with a duplicate column header causes real user data to be silently dropped and replaced with the wrong value, with the admin given no indication anything went wrong — they see a clean, error-free import and only discover the corruption later when users report wrong names/emails.

- **Duplicate email addresses within the file are imported as separate records with no error** (high)
  - Requirement: Email is the unique identity key for a user account (implicit in 'add users' — you cannot create two accounts for the same email). A bulk importer must treat a repeated key within the same batch as an unimportable/conflicting row, per the ticket's contract that rows that can't be imported are reported back.
  - Evidence: app/importer.py has no dedup or uniqueness check anywhere in the row loop; two rows with identical email values (e.g. from a merged HR export with an accidental duplicate) both land in `result.users` unmodified, with `result.errors` empty.
  - If shipped: Downstream account-creation logic either creates two accounts for the same person (rare and confusing) or fails/overwrites unpredictably on the second insert, and because the importer reported zero errors, the admin has no way to know from the tool that the source data had a conflict — they'll only find out when account creation fails or behaves inconsistently for that user.

- **Leading/trailing whitespace in field values is checked for emptiness but not stripped before being stored** (medium)
  - Requirement: The header is explicitly stripped ('column.strip()') establishing that whitespace-tolerant parsing is the intended behavior for this feature (customer-produced files with 'whatever they've got' formatting); the same tolerance is not applied to data values, which is inconsistent and produces corrupt identity data.
  - Evidence: app/importer.py:80-82 only calls `.strip()` on a *copy* used for the emptiness check (`record.get(c, '').strip()`); the value stored in `record` (and thus `result.users`) via `dict(zip(header, row))` at line 78 retains the raw, unstripped value. Verified: input ' ada@example.com ' is stored verbatim with surrounding spaces.
  - If shipped: Emails imported with leading/trailing whitespace (common from copy-pasted spreadsheet cells) will fail exact-match lookups, login, or invite-email delivery downstream, and 'Engineering ' vs 'Engineering' team values will silently fragment team groupings — with no error ever surfaced to the admin since the check that would have caught it only looked at the trimmed copy.

- **Required column names are matched case-sensitively, rejecting valid files with capitalized headers** (medium)
  - Requirement: The ticket states the source files are customer-produced ('HR exports, spreadsheets, whatever they've got') and does not mandate lowercase headers; a robust importer for uncontrolled third-party input must not hard-fail on a header casing convention the ticket never specified as required.
  - Evidence: app/importer.py:51 does `c not in header` for each of REQUIRED_COLUMNS, an exact case-sensitive string comparison. Verified: a header of 'Email,Name,Team' (a very common Excel/HR convention) is reported as missing all three required columns even though the data is otherwise complete and correct.
  - If shipped: Any customer whose export tool capitalizes column headers (extremely common, e.g. Workday, BambooHR, manually-built spreadsheets) has their entire import rejected outright, forcing the admin to manually edit the CSV before every upload — defeating the purpose of the bulk-import feature for a large fraction of real-world input files.

- **The email field is checked only for non-emptiness, not for being a plausible email address** (medium)
  - Requirement: A user-import feature that provisions accounts by email must validate that the identity key is a syntactically valid email before accepting the row, otherwise garbage rows corrupt the pipeline that consumes `result.users` (e.g. invite emails, SSO matching).
  - Evidence: app/importer.py:80-87 only checks `record.get(c, '').strip()` truthiness for REQUIRED_COLUMNS; there is no format check. Verified: a row with email value 'not-an-email' is accepted into `result.users` with no error.
  - If shipped: Malformed values (e.g. a name accidentally typed into the email column, or a mail-merge artifact) are silently accepted as valid users; account provisioning downstream either crashes on an invalid address or silently fails to deliver the invite, and the admin gets no error at import time pointing them to the bad row.

- **Reported error row numbers are physical line counts, not logical CSV row numbers, and diverge when any field contains an embedded newline** (low)
  - Requirement: The ticket requires errors to be 'human-readable problems' the admin can act on; a row number that does not correspond to the row the admin sees in their spreadsheet/file fails that requirement.
  - Evidence: app/importer.py:67 sets `line_num = reader.line_num`, which is Python csv's count of physical lines consumed, not logical rows. Verified: with a quoted field containing an embedded newline in row 1, a bad value in the very next logical row is reported as 'row 4' when it is actually the 3rd row (2nd data row) in the file/spreadsheet.
  - If shipped: For any customer file with a multi-line text field (addresses, notes, or any spreadsheet cell with a line break — a routine occurrence in HR exports named explicitly in the ticket), every error row number after that point is off, sending the admin to the wrong row when they try to fix the flagged problem.

- **No limit on input size before the whole file and all rows are buffered in memory** (low)
  - Requirement: An admin-facing upload endpoint accepting arbitrary customer-produced files should bound resource consumption; unbounded parsing of attacker- or accident-controlled input is a standard defensive-coding expectation for any upload feature, especially one whose contract says 'whatever they've got'.
  - Evidence: app/importer.py takes the entire `csv_text` into `io.StringIO` and accumulates every row into `result.users`/`result.errors` with no size, row-count, or column-count cap anywhere in the function.
  - If shipped: An admin (or a compromised/malicious admin account) uploading a very large or pathological file (e.g. megabytes of near-duplicate rows, or a file with extremely wide rows) can cause excessive memory use on the request-handling process; since this is the only bound in the import path, there's nothing else to stop it.
