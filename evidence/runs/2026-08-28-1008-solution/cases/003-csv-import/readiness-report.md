## What review found

### Raised by the first review, and sent to repair

- **A single oversized field raises an uncaught exception and aborts the entire import** (high)
  - Requirement: Ticket contract: 'A row that cannot be imported goes in errors... A file with unimportable rows still imports the rows that are fine.' Any single bad row must degrade to a reported error, not fail the whole request.
  - Evidence: app/importer.py:58 iterates `for line_number, row in enumerate(reader, ...)` with no try/except around the loop. Python's csv module enforces a field size limit (128KB) and raises `_csv.Error: field larger than field limit` when exceeded. Reproduced: a single field of ~200KB (e.g. a corrupted export or a pasted blob in one cell) causes `import_users` to raise instead of returning an ImportResult.
  - If shipped: One malformed/oversized row in an otherwise-valid 340-row HR export causes the whole upload to 500 instead of importing the 339 good rows and reporting one error, exactly the failure mode the ticket says must not happen. Since customer-produced files are explicitly uncontrolled input, this is a realistic and easily-triggered case, not a hypothetical.

- **Required-column check is case-sensitive, so a differently-cased header rejects the entire file** (high)
  - Requirement: Ticket: 'email, name and team must be present' — from customer-supplied HR exports/spreadsheets whose header casing is not controlled by us ('the files come from the customer's own systems... we don't control how they're produced').
  - Evidence: app/importer.py:51 does `column not in header` as an exact string match after only `.strip()`. Reproduced: header `Email,Name,Team` (capitalized, as many HR/spreadsheet exports produce) is reported as missing all three required columns and the whole file is rejected with zero rows imported.
  - If shipped: A perfectly valid file from a customer whose export tool capitalizes headers is rejected outright with a confusing 'missing required columns' error, even though the required data is present — this is exactly the class of file the feature was built to accept.

- **Duplicate email rows within one file are silently imported as separate users** (medium)
  - Requirement: Implicit requirement of a user-import feature: email is the identity key for a user account, so two rows with the same email (including case-insensitive dupes) must not silently produce two accounts or two conflicting records.
  - Evidence: app/importer.py has no dedup/uniqueness check across `result.users`. Reproduced: a file with `ada@example.com` appearing twice with different names/teams produces two entries in `result.users`, no error.
  - If shipped: HR exports commonly contain duplicate rows (e.g. a user listed under two teams, or a re-exported row). Downstream user-creation will either error confusingly per-row, silently overwrite one record with another, or create duplicate accounts — and the admin gets no warning from the importer that this happened.

- **A repeated column name in the header silently overwrites earlier values with no error** (medium)
  - Requirement: Ticket: 'Rows that can't be imported get reported back to the admin' — data loss from an ambiguous header should be surfaced, not silently swallowed.
  - Evidence: app/importer.py:69 builds the record with `{name: value for name, value in zip(header, row)}`. Reproduced: header `email,name,team,email` with a row `a@example.com,Ada,Eng,other@example.com` produces `email: 'other@example.com'`, silently discarding the first email column's value with no error or warning.
  - If shipped: A malformed or accidentally duplicated export column (easy to produce from a spreadsheet with a stray copy-pasted column) causes one of the user's real field values to vanish without any indication to the admin that data was dropped.

- **Reported row numbers do not match physical file lines when a field contains an embedded newline** (low)
  - Requirement: RFC 4180 permits quoted fields to contain embedded newlines; the ticket implies errors are 'reported back to the admin' so they can find and fix the offending row in their source file.
  - Evidence: app/importer.py:58 uses `enumerate(reader, start=2)`, which counts logical CSV records, not physical text lines. Reproduced: a file where row 2 contains a quoted multi-line name causes the next data row (physical line 4) to be reported as 'Row 3', an off-by-one (or more, depending on how many embedded newlines preceded it) mismatch against the actual file.
  - If shipped: An admin trying to locate 'Row 3' in a text editor or spreadsheet to fix the reported error will look at the wrong line, especially in larger files with several multi-line fields, making the error report actively misleading rather than merely imprecise.

- **Field values are stored verbatim, including spreadsheet-formula payloads** (low)
  - Requirement: OWASP CSV Injection guidance: untrusted CSV cell values beginning with `=`, `+`, `-`, `@` (or tab/CR) must be neutralized before the data is later rendered or re-exported into a spreadsheet, since the source file is explicitly untrusted customer input.
  - Evidence: app/importer.py:69 only applies `.strip()` to each cell; no check or escaping for formula-trigger characters is performed before values land in `result.users`.
  - If shipped: If the admin UI or any downstream tooling later exports the imported user list back to CSV/Excel (a common admin convenience action), a name/team field crafted as `=HYPERLINK(...)` or `=cmd|'/c calc'!A1` from a compromised or malicious customer export can execute on the admin's machine when opened.


### Still flagged after the repair pass

- **CSV-injection mitigation mutates the stored email/name/team values themselves, not just a display copy** (high)
  - Requirement: The imported record's email must be the literal, correct account identifier the customer supplied (contract: `result.users` feeds account provisioning/login, not a spreadsheet render). The OWASP CSV-injection mitigation (prefixing =,+,-,@ with an apostrophe) is meant to be applied when *rendering/exporting* data back into a spreadsheet, not when ingesting the source-of-truth value.
  - Evidence: app/importer.py:103-106,138-146 — `_sanitize_cell` is applied to every cell before validation/storage. Any email, name, or team starting with '=', '+', '-', or '@' gets a literal apostrophe prepended and that mutated string is what ends up in `result.users`. Verified: `+alerts@example.com` is stored as `'+alerts@example.com`; `@example.com` is stored as `'@example.com`; a team named `-Ops` is stored as `'-Ops`.
  - If shipped: Any legitimate email using plus-addressing, or any name/team beginning with a hyphen (common in HR exports, e.g. '-TEMP', '-Contractor'), silently gets a corrupted value baked into the account record with no error reported. The admin sees a clean import with zero errors, but the created account's email no longer matches what the customer's HR system has, breaking SSO/login and any downstream email delivery to that user.

- **Classic Mac / lone-CR line endings crash the whole upload instead of being reported as an error** (high)
  - Requirement: Ticket: "Rows that can't be imported get reported back to the admin, and the rest of the file still imports" and "we don't control how [files] are produced." A parser accepting arbitrary customer-produced files must not raise an unhandled exception for a file it cannot parse.
  - Evidence: app/importer.py:44-48 — the header line is read via `next(reader)` guarded only by `except StopIteration`, with no `except csv.Error`. A file using bare `\r` line endings (old Mac exports, some legacy HR/mainframe tooling) causes `io.StringIO` to yield the whole file as one line, and `csv.reader` raises `_csv.Error: new-line character seen in unquoted field` on the very first `next(reader)` call. Reproduced directly: `import_users('email,name,team\rada@example.com,...\r')` raises uncaught.
  - If shipped: The admin upload endpoint gets an unhandled exception (likely a 500) instead of a clean 'file could not be read' or per-row error result, for a file format variant that is squarely within the stated 'whatever they've got' scope. The 340-user onboarding this ticket exists to speed up fails outright with no diagnostic message.

- **Email validation only checks for the presence of '@', accepting structurally invalid addresses** (medium)
  - Requirement: Ticket: rows that can't be imported must be reported as errors, not silently added to `result.users`. An address that is not a deliverable email is a row that 'can't be imported' for a feature whose entire purpose is provisioning login/notification accounts.
  - Evidence: app/importer.py:111 — validation is `elif "@" not in record["email"]`. Verified `ada@` (no domain), `@example.com` (no local part), and `a@b@c` (multiple '@') all pass validation and land in `result.users` with zero errors.
  - If shipped: Malformed addresses from messy HR exports are silently provisioned as real user accounts instead of being flagged for the admin to fix, producing accounts that can never receive an invite/notification email and that the admin has no indication need correcting.

- **Semicolon-delimited exports (common from EU-locale Excel) are rejected with a misleading 'missing column' error** (low)
  - Requirement: Ticket: "The files come from the customer's own systems ... whatever they've got — so we don't control how they're produced." No delimiter detection is attempted, and the resulting error misrepresents the actual problem.
  - Evidence: app/importer.py:43 — `csv.reader` is constructed with default comma delimiter and no `csv.Sniffer`/dialect detection. A semicolon-delimited file with all three required columns present produces `errors: ['Missing required column(s): email, name, team']`, which is factually wrong (the columns are present, just not comma-separated).
  - If shipped: Admins receive a confusing error that says required columns are missing when the file actually has them, for a very common real-world export variant (Excel in most European locales defaults CSV export to semicolons because comma is the decimal separator), wasting support time diagnosing a self-inflicted red herring.
