## What review found

### Raised by the first review, and sent to repair

- **request_reset() has a fast-path/slow-path timing difference that leaks account existence** (medium)
  - Requirement: The service's own stated contract (app/auth.py:96, 'Don't reveal whether an account exists') and OWASP Forgot Password Cheat Sheet's requirement that response behavior be indistinguishable for existing vs. non-existing accounts, including timing.
  - Evidence: app/auth.py:94-109 — for an unknown email the method returns immediately after a single dict lookup; for a known email it generates a token, writes to _tokens, formats a link, and calls mailer.send(). No constant-time/dummy-work path exists for the unknown-email branch.
  - If shipped: An attacker measuring response latency (especially once Mailer is a real network call, e.g. SMTP/SES) can distinguish registered from unregistered emails and enumerate the user base, exactly the outcome the in-code comment says the implementation is trying to prevent.

- **Requesting a new reset link does not invalidate previously issued, still-valid tokens for the same user** (medium)
  - Requirement: OWASP Forgot Password Cheat Sheet: 'Old, unused password reset tokens ... expire after a set time or, ideally, after the user makes a new request' — only the most recently issued reset token should be usable.
  - Evidence: app/auth.py:99-101 — request_reset() always mints a fresh token and adds it to self._tokens without looking up or removing any prior (email, expiry) entries already stored for that email.
  - If shipped: A user who clicks 'forgot password' twice (or an attacker who triggers repeated reset emails) leaves multiple simultaneously-valid links live for up to an hour. An old email sitting in an inbox, a mail relay log, or a shared/compromised mailbox remains a valid credential-reset vector even after the user believes they've completed the flow with a later link.

- **A successful password reset does not revoke other outstanding tokens for the same account** (medium)
  - Requirement: OWASP Forgot Password / Session Management guidance: once a reset token is redeemed, all other live reset tokens for that account should be invalidated, since they represent parallel, unaccounted-for paths to change the credential.
  - Evidence: app/auth.py:111-128 — reset_password() deletes only the single token key that was redeemed (line 127); it never scans/purges other entries in self._tokens whose stored email matches the same user.
  - If shipped: If two reset emails were sent (e.g., user retried, or an attacker triggered a reset to phish/intercept a link) and the legitimate user redeems one, the other token remains valid until its own expiry, giving an attacker who obtained the second link a window to reset the password again after the legitimate user thinks the account is secured.

- **No confirmation/notification email is sent after a password reset succeeds** (medium)
  - Requirement: OWASP Forgot Password Cheat Sheet: 'Notify the user of password change' — a separate email confirming the credential was changed must be sent so the legitimate owner can detect and react to an unauthorized reset.
  - Evidence: app/auth.py:111-128 — reset_password() updates user.password_hash and returns True, but calls self.mailer.send(...) nowhere in this method; only request_reset() ever emails the user.
  - If shipped: If an attacker who intercepted or guessed a valid token resets the password, the real account owner receives no signal that their credential changed, delaying detection of account takeover.

- **Expired reset tokens are only removed when someone attempts to redeem them, so unredeemed tokens are never cleaned up** (low)
  - Requirement: Lifecycle/resource-management expectation for any TTL-based token store used by a long-running service: expired entries must not accumulate unboundedly in memory just because no one happened to look them up.
  - Evidence: app/auth.py:117-119 and :113 — the only code paths that call `del self._tokens[token]` are inside reset_password(), which only runs for a token someone actually submits. request_reset() never sweeps or bounds self._tokens, and there is no background/periodic purge.
  - If shipped: In production, every forgot-password request that is never completed (user ignores the email, link expires unclicked) leaves a permanent dict entry. Over the service's lifetime this is unbounded memory growth, and is trivially acceleratable by anyone repeatedly POSTing known/guessed emails to request_reset(), turning it into a low-cost memory-exhaustion vector against a long-lived process.


### Still flagged after the repair pass

- **Reset tokens live only in a per-instance Python dict** (high)
  - Requirement: A password-reset link must remain valid for its full TTL regardless of which process or server handles the follow-up request — an implicit lifecycle requirement of any multi-request flow (request happens on one HTTP call, redemption on a later, possibly different, call).
  - Evidence: app/auth.py:92 — `self._tokens: dict[str, tuple[str, float]] = {}` is instance state with no backing store (file, cache, DB). `PasswordResetService` is constructed fresh per call site with no shared persistence layer.
  - If shipped: In any production deployment with more than one worker process/thread pool, container replica, or a deploy/restart between the two clicks, the token minted in request_reset on instance A will not exist on instance B (or after a restart) when reset_password is called. Legitimate users clicking a valid, unexpired link get 'invalid token' and the four-a-week support burden this ticket was meant to eliminate returns.

- **reset_password accepts any new_password, including empty string** (high)
  - Requirement: A password-reset endpoint must enforce the same minimum password policy as account creation (NIST SP 800-63B minimum length / OWASP Authentication Cheat Sheet) — a reset must not be a backdoor around registration-time password rules.
  - Evidence: app/auth.py:134-147 — `reset_password` calls `hash_password(new_password)` unconditionally; there is no length, emptiness, or complexity check anywhere in the method.
  - If shipped: A user (or an attacker who obtained a token via a shared device or leaked email) can set the account password to `''` or `'a'`, silently downgrading account security below whatever bar registration enforces, and support has no record of it happening.

- **Full reset token is kept in memory as the dict key, not a hash of it** (medium)
  - Requirement: OWASP Forgot Password Cheat Sheet: the reset token, like a password, should be stored server-side as a hash, so possession of the server's memory/log/dump does not itself grant the ability to redeem outstanding tokens.
  - Evidence: app/auth.py:113-119 — `token = new_token()` ... `self._tokens[token] = (email, expires_at)` stores the raw, usable token verbatim as the dictionary key.
  - If shipped: Any process-memory disclosure, core dump, or accidental debug log of `self._tokens` hands an attacker live, redeemable reset tokens for every user with an outstanding request, equivalent to leaking their new-password credentials directly.

- **request_reset has no throttling per email or per caller** (medium)
  - Requirement: OWASP Forgot Password Cheat Sheet requires rate-limiting / lockout on the reset-request endpoint to prevent abuse (mail-bombing a victim's inbox, resource exhaustion).
  - Evidence: app/auth.py:107-132 — `request_reset` performs `self.mailer.send(...)` on every single call with no counter, cooldown, or per-address cap.
  - If shipped: An attacker can call `request_reset('victim@example.com')` in a tight loop to flood the victim's inbox with reset emails (harassment / mail-bombing), or hammer the mailer/backing SMTP service to exhaust it, with no defense in this layer.

- **self._tokens is mutated without any concurrency control** (medium)
  - Requirement: A service invoked from a multi-threaded/multi-request web server must keep shared mutable state consistent under concurrent calls (basic thread-safety expectation for 'two attempts at once').
  - Evidence: app/auth.py:94-105 — `_prune_expired` and `_invalidate_tokens_for` each build a list of keys then `del self._tokens[t]` in a second pass, with no lock; `request_reset`/`reset_password` read-then-write `self._tokens` and `user.password_hash` with no synchronization.
  - If shipped: Two concurrent calls (e.g. two in-flight requests for the same email, or a client retry racing the original request) can both pass the expiry/removal check for the same key and the second `del self._tokens[t]` raises `KeyError`, crashing the request; concurrent redemption/invalidation can also race and leave inconsistent state.

- **Email is looked up in the user store with exact-string matching** (low)
  - Requirement: Standard practice for account-lookup email handling (and most mail providers' actual case-insensitive treatment of the local-part) is to normalize email addresses before comparison, so a user who types their address in a different case can still find their account.
  - Evidence: app/auth.py:115 — `user = self.users.get(email)` does a raw dict lookup with no case-folding or trimming of the input email.
  - If shipped: A user who signed up as 'Ada@Example.com' but types 'ada@example.com' (or vice versa) when requesting a reset silently gets the generic 'if an account exists' email and no actual reset link, reintroducing the support burden this feature was built to remove.
