## What review found

### Raised by the first review, and sent to repair

- **A processor failure (5xx) is cached permanently against the idempotency key, blocking all future legitimate retries** (high)
  - Requirement: Idempotency-key semantics (Stripe's documented contract, which this design mirrors): only the definitive outcome of a completed attempt should be memoized so that a client can safely retry after a transient/ambiguous failure and eventually get a real result. An error caused by the processor itself must not permanently lock the key to that error.
  - Evidence: app/charges.py post_charge: `status, body = self._execute(params)` followed unconditionally by `self._idempotency_cache[idempotency_key] = (status, body)` -- this runs the same way whether `_execute` returned 200 or the simulated 500 'processor unavailable'. Any subsequent call with the same key hits the cache-hit branch at the top of `post_charge` and returns the stale 500 without ever calling `_execute` again.
  - If shipped: This is exactly the scenario PAY-208 exists to fix: the mobile SDK retries automatically with the same key after a dropped/failed request. If the first attempt failed with a transient processor error, every automatic retry now returns the cached 500 forever -- the charge can never succeed with that key. The customer's checkout is permanently stuck, support reopens the same class of ticket, and the likely 'fix' (mint a new idempotency key on error and retry) reintroduces the double-charge risk this feature is supposed to eliminate, since the original 500 may have been an ambiguous outcome where the processor actually moved money.

- **Two simultaneous requests with the same idempotency key both pass the cache-miss check and both execute the charge** (high)
  - Requirement: Idempotency-key contract for concurrent duplicate requests: a second request arriving with a key that is already in flight must not be allowed to independently execute the side effect -- it must either wait/lock or be rejected (e.g. HTTP 409 'a request with this idempotency key is already in progress'), never race to a second `_execute`.
  - Evidence: app/charges.py post_charge implements a check-then-act sequence with no lock: `if idempotency_key ... in self._idempotency_cache: return ...` then later `self._idempotency_cache[idempotency_key] = (status, body)`. Nothing marks the key as 'in progress' between the cache check and the cache write, and `_execute` (and `before_execute`, which Operations explicitly monkey-patches to inject latency) sits in between with no synchronization.
  - If shipped: The ticket's own root cause is a dropped connection triggering a client retry while the original request may still be in flight upstream. If the retry races the original before the first `_execute` call returns and writes the cache entry, both calls see a cache miss, both call `_execute`, and the customer is charged twice -- the exact double-charge bug this feature was built to close, now happening through the idempotency path itself instead of around it.

- **Reusing a key with a different request body silently returns the stale cached charge instead of rejecting the mismatch** (medium)
  - Requirement: Standard idempotency-key semantics (as documented by Stripe and other processors this pattern imitates): a key must be scoped to one specific request payload. Replaying the same key with different parameters (different amount, currency, etc.) must return an error, not the cached result for the original, different request.
  - Evidence: app/charges.py post_charge only keys the cache on `idempotency_key` and never compares the incoming `params` against the params that produced the cached entry: `if idempotency_key is not None and idempotency_key in self._idempotency_cache: return self._idempotency_cache[idempotency_key]`.
  - If shipped: A client bug or key-collision (e.g. a poorly-generated key, or a UI that reuses a key across a corrected order) causes a request for one amount to silently receive a 200 confirming a charge for a different amount that was never actually made for the new params. The caller believes a $X charge succeeded when only the original $Y charge exists on the ledger -- a billing-integrity defect a payments reviewer would block on.

- **Idempotency keys and their cached responses live forever with no TTL, unlike the standard window this pattern is modeled on** (medium)
  - Requirement: Idempotency-key lifecycle convention (e.g. Stripe expires keys after 24 hours): keys must expire after a bounded window so storage doesn't grow without bound and so the same key value can legitimately be reused for a new operation after the window passes.
  - Evidence: app/charges.py: `self._idempotency_cache: dict[str, tuple[int, dict]] = {}` is written to in `post_charge` and never pruned or checked against `self.clock.now()`. The injected `Clock` (with its `advance()` method, clearly provided for exercising time-based expiry) is never consulted anywhere in `post_charge`.
  - If shipped: In production the cache grows unbounded for the lifetime of the process, and a key can never be reused even long after the original transaction context is irrelevant, contradicting how every real idempotency-key implementation this feature is modeled on actually behaves. This also means capacity/memory planning for the service is impossible to reason about.


### Still flagged after the repair pass

- **An exception during _execute()/before_execute() permanently strands the key in 'in_progress', blocking every legitimate retry for 24h** (high)
  - Requirement: The ticket's own stated goal: 'the client's connection drops, it retries the charge... if we see the same key again we shouldn't put a second charge through' implies a retry after a failed/interrupted attempt must eventually be able to complete. The claim-then-execute-then-release logic in post_charge has no try/finally, so any exception between the claim (line 129) and the cache update (line 145) leaves the entry as status='in_progress' forever, with nothing to release it short of the 24h TTL.
  - Evidence: app/charges.py post_charge: the block from 'self._idempotency_cache[idempotency_key] = {...status: in_progress...}' through '_execute(params)' and the final cache update has no exception handling. Reproduced: monkey-patching before_execute to raise ConnectionError (simulating exactly the 'processor call fails/connection drops' scenario Operations is documented to inject via before_execute) leaves the cache entry stuck at status='in_progress'; a subsequent retry with the corrected/working call gets HTTP 409 'already in progress' instead of completing, and api.executed stays empty.
  - If shipped: The exact scenario PAY-208 was filed to fix -- a dropped connection followed by a client retry -- now results in the customer's charge never going through at all for up to 24 hours, instead of a double charge. This trades double-charge tickets for 'my payment is stuck/rejected' tickets, which for a P1 payments endpoint is arguably worse since the merchant now believes the charge failed and may abandon checkout.

- **_prune_expired deletes idempotency entries by age alone, including ones still status='in_progress', letting a concurrent/late retry bypass the in-progress guard and execute a second real charge** (high)
  - Requirement: Idempotency-key semantics (mirrored from Stripe, per the code's own comment) require that a key which is currently being processed cannot be reused to trigger a second attempt -- 'two attempts at once' must collapse to one execution regardless of elapsed time. An in-flight claim must never lapse purely due to TTL; only completed (done) entries should expire.
  - Evidence: app/charges.py:97-103 _entry_expired/_prune_expired check only entry['created_at'] and the fixed TTL, never entry['status']. Reproduced: seeding the cache with a status='in_progress' entry, advancing the injected Clock past the 24h TTL, then calling post_charge with the same key causes _prune_expired to delete the stale-but-still-in-flight claim, after which the request is treated as brand new and executed for real (HTTP 200, a genuine _execute call) instead of returning 409.
  - If shipped: If an original attempt is slow, hung, or (combined with the missing try/finally above) permanently stuck 'in_progress', any retry that arrives after the 24h window silently executes a second real charge against the processor instead of being deduplicated -- the double-charge bug the ticket exists to prevent, just delayed by up to a day.

- **Cached idempotency entries store the caller's params dict by reference, not a copy, so post-call mutation of that dict defeats the 'same key, different params → reject' check** (medium)
  - Requirement: Idempotency-key contract requires that reusing a key with materially different request parameters be rejected (the code implements this via entry['params'] != params at line 120), which implicitly requires the recorded params to be an immutable snapshot of what was actually charged.
  - Evidence: app/charges.py stores '"params": params' directly (lines 131 and 151) instead of a copy such as dict(params). Reproduced: calling post_charge(params, key='k1'), then mutating params['amount'] in place before calling post_charge(params, key='k1') again causes the second call to be treated as identical (no 409), returning the cached first response -- silently masking that the second call actually requested a different amount.
  - If shipped: Any caller pattern that reuses/mutates the same dict object across a retry (common with retry helpers, middleware that annotates the body, or connection-pooled request objects) can cause a request for a different amount to silently return a stale cached response instead of being rejected, corrupting what the ledger/response tells the client actually happened.

- **The idempotency cache and lock are in-memory and process-local, so retries routed to a different instance (or after a restart) are not deduplicated at all** (high)
  - Requirement: A production idempotency-key implementation for a horizontally scaled payments service must make the dedup state visible to whichever instance handles the retry -- otherwise the guarantee only holds by accident of load-balancer stickiness.
  - Evidence: app/charges.py:__init__ defines self._idempotency_cache and self._lock as plain in-process dict/threading.Lock with no persistence or shared-store backing; there is no mechanism for a second ChargeAPI instance (a second process/pod) to see a claim made by another.
  - If shipped: In any real deployment with more than one process (which is the norm for a payments endpoint under a P1 double-charge incident), a dropped-connection retry that lands on a different instance -- or any retry after the original process restarts/redeploys -- bypasses the idempotency check entirely and re-executes the charge, reproducing the exact double-charge incidents PAY-208 was filed to close.

- **idempotency_key accepts any string of any length/content with no size or format limit** (low)
  - Requirement: Published idempotency-key implementations (e.g. Stripe's, referenced in this file's own TTL comment) bound the key to a reasonable length (Stripe: max 255 characters) precisely because the key is used as an unbounded-lifetime cache key.
  - Evidence: app/charges.py post_charge only checks 'idempotency_key is None'; there is no length or character-set validation before using it as a dict key that persists in _idempotency_cache for up to 24 hours.
  - If shipped: A malicious or buggy client can send arbitrarily large keys (megabytes each) repeatedly, growing the in-memory cache unbounded until the TTL sweep catches up, a low-cost memory-exhaustion vector against a payments endpoint.
