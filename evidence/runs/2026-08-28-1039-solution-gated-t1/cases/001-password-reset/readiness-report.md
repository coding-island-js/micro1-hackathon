## What review found

### Raised by the first review, and sent to repair

- **Outstanding reset tokens for an account are never invalidated when a newer one is issued or one is successfully used** (high)
  - Requirement: Standard forgot-password lifecycle rule (OWASP Forgot Password Cheat Sheet): a reset token must be single-use, and once a password has been reset — or a fresh reset is requested — all other outstanding tokens for that identity must stop working. Otherwise a stale link keeps a live door open to the account.
  - Evidence: app/auth.py:94-124 — `request_reset` appends a new `(email, expiry)` entry to `self._tokens` on every call without touching any prior entries for the same email; `reset_password` only deletes the single token it was given, leaving every other still-unexpired token for that same email fully valid.
  - If shipped: If a user (or an attacker who triggered extra reset emails, or an old email that leaked from a mail server/log) has more than one reset link outstanding, using one to change the password does not revoke the others. Anyone still holding an older link — including one issued before the account owner intentionally reset their password — can silently reset the password again within the 30-minute window, defeating the purpose of a completed reset.

- **reset_password will happily set the account's password to the empty string** (medium)
  - Requirement: A self-service 'set a new password' step must reject a blank/empty new password; shipping a reset flow that can leave an account with no effective password is a basic password-handling requirement (cf. NIST 800-63B minimum length rules, and general auth hygiene).
  - Evidence: app/auth.py:108-124 — `reset_password` takes `new_password`, does zero length/content validation, and calls `hash_password(new_password)` directly, so `reset_password(token, "")` returns True and stores `hash_password("")`.
  - If shipped: A user (or attacker who has captured a valid token, e.g. via a shared mailbox or log line) can set the account's password to an empty string. Depending on how the login endpoint later handles an empty submitted password, this can either lock the legitimate user out or, if the login form allows submitting empty, allow trivial login with no password at all.

- **request_reset uses an exact-string dict lookup on email, so a case-variant of a registered address silently gets no reset email** (low)
  - Requirement: Common self-service account-recovery convention: the domain part of an email address is case-insensitive per RFC 5321/1035, and virtually all mailbox providers also treat the local part case-insensitively in practice, so account lookup for a recovery flow is expected to be case-insensitive (or at least normalized), not a raw dict key match.
  - Evidence: app/auth.py:94-96 — `if email not in self.users: return` does a literal string membership check against `self.users` keys with no normalization, so a stored key of `ada@example.com` will not match a submitted `ADA@example.com`.
  - If shipped: A legitimate user who registered as `ada@example.com` but types `Ada@Example.com` (e.g. autocapitalized by their phone, or copy-pasted from an email client that title-cases it) gets no error and no email — the request is silently swallowed — appearing to the user as 'forgot password is broken', generating exactly the kind of support load this ticket exists to eliminate.


### Still flagged after the repair pass

- **Requesting a new reset link leaves all previously issued tokens for that user still valid** (high)
  - Requirement: OWASP Forgot Password Cheat Sheet: a password-reset token store should only honor a single active token per user — issuing a new reset link must invalidate any earlier outstanding link for that account, since the user (or an attacker who has intercepted an old email) should not be able to redeem a stale link once a fresher one has been issued.
  - Evidence: app/auth.py:108-121 — request_reset() calls new_token(), stores it in self._tokens keyed by the new token, and never calls self._invalidate_tokens_for(user_key) before adding the new one. Tellingly, the code already implements _invalidate_tokens_for and does call it on a *successful password change* (auth.py:142), showing the author understood the need to revoke outstanding tokens but only wired it up for one of the two places it's required.
  - If shipped: A user who clicks 'forgot password' twice (e.g. because the first email was slow to arrive, or was sent to a shared/leaked inbox) leaves the first link live for the full 30-minute TTL. Anyone who obtains that first email — via mail forwarding, a compromised mail provider, shoulder-surfing a notification preview, or simple interception — can still reset the account's password even though the legitimate user believes only the newest link is valid. This is the exact scenario the 'invalidate on reissue' rule exists to close.
