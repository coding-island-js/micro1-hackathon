## What review found

### Raised by the first review, and sent to repair

- **A single row that trips a csv.Error (e.g. an oversized field) discards the entire file, not just that row** (high)
  - Requirement: Ticket: 'Rows that can't be imported get reported back to the admin, and the rest of the file still imports.'
  - Evidence: app/importer.py:42-46 does `rows = list(csv.reader(io.StringIO(text)))` inside a single try/except. csv.reader raises csv.Error for things that happen mid-file (e.g. a field over the 128KB field_size_limit), so one bad row anywhere in a 340-row customer file aborts parsing of the whole file and every valid row is lost, with only a single generic error string returned.
  - If shipped: An admin uploads a 340-row HR export where one row has an oversized/garbled field (common in real exports with pasted rich text or huge notes columns). Instead of importing 339 good users and reporting 1 bad row, the admin gets zero users imported and one opaque 'could not parse file' message, with no indication which row or why.

- **An unterminated quote in one row silently merges all following rows into it, dropping later valid users with no error reported for them** (high)
  - Requirement: Ticket: 'Rows that can't be imported get reported back to the admin, and the rest of the file still imports.'
  - Evidence: app/importer.py uses csv.reader on the whole file at once. RFC 4180-style quoting means an unclosed `"` causes the reader to treat every subsequent newline as embedded inside that one quoted field until EOF, producing a single malformed 'row' out of what were several good data lines. Only one error ('row 2: expected 3 columns, got 1') is emitted; the users on the swallowed lines (e.g. bob@example.com, carol@example.com) vanish with no error naming them at all.
  - If shipped: A stray/unbalanced quote character anywhere in a customer-produced CSV (very plausible given 'we don't control how they're produced') causes every user after that point in the file to be silently dropped -- not reported as errors, not imported. The admin believes the file imported (modulo one reported bad row) while dozens of real users never got created and nothing flags that they're missing.

- **A header with a repeated column name silently overwrites one value with another and reports no error** (medium)
  - Requirement: Ticket: 'any other columns come through as-is' -- implies no field is silently discarded; a row that can't be faithfully represented should be reported, not corrupted
  - Evidence: app/importer.py:56 checks `col not in header` only for presence, never checks header uniqueness. Line 73 builds `record = {col: value.strip() for col, value in zip(header, row)}`, so if the header contains the same column name twice (e.g. two 'email' columns, or two 'notes' columns -- plausible in a merged HR export), the first value for that column is silently overwritten by the last, with `result.errors` empty and the row imported as if nothing were wrong.
  - If shipped: A customer export with a duplicated column (common when spreadsheets are merged from two source systems) causes one of the two values to vanish per affected row -- e.g. the real corporate email is overwritten by a personal email pasted into a second 'email' column -- and the admin has no error message telling them any data was lost.

- **Required column matching is case-sensitive, so headers like 'Email'/'Name'/'Team' from real customer exports are rejected outright** (medium)
  - Requirement: Ticket: files come from 'the customer's own systems -- HR exports, spreadsheets, whatever they've got -- so we don't control how they're produced'; the importer should tolerate reasonable variation in files it doesn't control
  - Evidence: app/importer.py:56 does `col not in header` doing exact string equality against lowercase REQUIRED_COLUMNS, with no case normalization. Spreadsheet exports (Excel, Google Sheets, Workday) very commonly title-case or capitalize headers ('Email', 'Name', 'Team'). Such a file is rejected wholesale with 'missing required column(s): email, name, team' even though the required data is present, verbatim, under different capitalization.
  - If shipped: An admin uploads a perfectly valid customer export whose header row happens to be capitalized differently than the literal lowercase strings the code expects, and the entire 340-row file is rejected with a confusing 'missing column' error even though every required column is present.


### Still flagged after the repair pass

- **Splitting the CSV into physical lines before parsing corrupts quoted fields with embedded newlines, and silently drops/mangles subsequent valid rows** (high)
  - Requirement: RFC 4180 §2.6: a field may contain line breaks if the field is enclosed in double quotes; the standard library's own csv module supports this when fed the whole stream. The ticket also requires: 'A file with unimportable rows still imports the rows that are fine' — but here a well-formed row causes a *different*, otherwise-valid row to fail too.
  - Evidence: app/importer.py:42-52 and 82-84: the code does `text.splitlines()` and then re-parses each individual line separately with `csv.reader(io.StringIO(line))`, rather than parsing the full text as one stream. A single logical CSV row that spans multiple physical lines (a quoted field containing '\n', which is valid CSV and common in spreadsheet/HR exports containing notes or addresses) is torn into two malformed fragments. Confirmed via direct execution: feeding the stdlib `csv.reader` the whole text stream correctly parses the multiline row, but the importer's line-based approach produces two bogus 'expected 3 columns' errors and drops the legitimate second data row.
  - If shipped: An admin uploads a genuine HR export where one field (e.g. a name, note, or address column) contains an embedded newline inside quotes — a completely ordinary CSV produced by Excel or Google Sheets. The importer doesn't just fail that one row: it desynchronizes line numbering for every row after it, so subsequent good rows (e.g. 'b@example.com') get shown as parse errors and are silently excluded from the import, with confusing/incorrect row numbers in the error messages. Admins onboarding real customer files (which is exactly the ticket's stated use case) will lose real users without a way to tell which rows are actually broken.
