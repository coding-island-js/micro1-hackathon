## What review found

### Raised by the first review, and sent to repair

- **A transient processor failure (5xx) is cached under the idempotency key, so every future retry with that key is stuck returning the same failure even after the processor recovers** (high)
  - Requirement: Idempotency-key semantics for a payments retry path: only terminal, well-defined outcomes (success, or a definitive client-side rejection of that exact request) should be memoized and replayed. A 5xx from the upstream processor is by definition an indeterminate/transient failure -- the whole point of retry-with-idempotency-key (per the ticket's own motivating scenario: 'connection drops, client retries') is that the retry gets a real second attempt at the processor, not a frozen replay of the failure.
  - Evidence: app/charges.py:99-100 -- `if idempotency_key is not None: self._idempotency_cache[idempotency_key] = (status, body)` runs unconditionally on every status code, including the 500 branch of `_execute` (line 83-84, `simulate == 'processor_down'`), which is a hook clearly provided for testing exactly this failure/retry path.
  - If shipped: A customer whose charge attempt hits a transient processor outage (proxy timeout, brief upstream 5xx) can never be charged again on that idempotency key, even seconds later once the processor is healthy again. Support sees a customer stuck permanently unable to check out; the client-side retry loop that PAY-208 exists to protect just keeps re-serving the cached 500 forever.

- **Reusing the same idempotency key with different request parameters silently returns the first charge's cached response instead of erroring** (high)
  - Requirement: Idempotency-key contract: a key identifies one specific request body, not just 'this customer's intent right now'. If a key is reused with a materially different payload (different amount/currency), the server must reject the second call rather than pretend it succeeded with different numbers than what was actually charged.
  - Evidence: app/charges.py:90-91 -- the cache lookup `if idempotency_key is not None and idempotency_key in self._idempotency_cache: return self._idempotency_cache[idempotency_key]` happens before params are even inspected, so it returns the first charge's body regardless of whether the new params match.
  - If shipped: A client bug (or key-derivation collision) that reuses a key for a $99.00 charge after an earlier $25.00 charge on the same key gets back `200 succeeded, amount: 2500` -- the client's UI shows the wrong amount as charged, or believes the $99 charge went through when it never did and no error was ever surfaced. This is a reconciliation/financial-correctness defect a payments reviewer would block on.

- **Two requests with the same idempotency key arriving before the first has finished are not deduplicated -- both execute and both charge** (high)
  - Requirement: The ticket's own stated goal: 'if we see the same key again we shouldn't put a second charge through.' The dominant real-world cause of double charges from a dropped-connection retry is that the original request is still in flight server-side when the retry arrives, not that it neatly completes before the retry starts.
  - Evidence: app/charges.py:89-102 -- the key is only written into `self._idempotency_cache` after `_execute` returns (line 99-100). Nothing reserves the key at the start of the call, so a second call with the same key that arrives while the first is still inside `_execute` finds nothing in the cache, passes validation, and calls `_execute` again -- a second ledger entry, a second charge.
  - If shipped: Exactly the double-charge scenario in the ticket's own motivating incident: mobile client's connection drops, SDK retries immediately while the original request is still being processed server-side, both requests reach `_execute`, customer is billed twice. This is the P1 the ticket was filed to fix, and it is still possible.

- **Idempotency cache entries never expire and the injected Clock is never consulted for expiry** (low)
  - Requirement: Standard idempotency-key implementations bound key lifetime (e.g. 24h) so memory doesn't grow unbounded and so a key can eventually be reused for a genuinely new request; the ticket explicitly calls out injecting `Clock` for time-dependent logic ('Take time from the injected Clock, never time.time()'), implying time-based behavior was expected somewhere in this feature.
  - Evidence: app/charges.py:58,90-100 -- `_idempotency_cache` is a plain dict with no timestamp or eviction logic, and `self.clock` is never referenced anywhere in `post_charge`.
  - If shipped: In a long-running process, `_idempotency_cache` grows without bound as an unbounded memory leak, and a key can never be legitimately reused even after the operation it referred to is long settled. No specific TTL is stated in the ticket, so I can't demonstrate a concrete boundary violation with a test.


### Still flagged after the repair pass

- **A retry with the same idempotency key after a processor error triggers a second real charge attempt** (high)
  - Requirement: Ticket: 'if we see the same key again we shouldn't put a second charge through' and the documented ledger contract: 'self.executed is the ledger of what the upstream processor actually attempted. One entry = money moved once.' A second attempt under the same key must not produce a second ledger entry.
  - Evidence: app/charges.py lines 118-122: on status >= 500 the implementation does `del self._idempotency_cache[idempotency_key]` after `_execute` has already appended an attempt to `self.executed`. The very next call with the same key (the mobile SDK's automatic retry) finds no cache entry, treats the request as brand-new, and calls `_execute` again, appending a second entry to `self.executed`.
  - If shipped: This is exactly the double-charge scenario PAY-208 was opened to fix: connection/processor trouble followed by an automatic client retry with the same idempotency key. Per the class's own ledger contract ('one entry = money moved once'), two entries means the customer was billed twice. Support gets a fourth double-charge ticket, this time for the retry path the feature was explicitly built to close.
