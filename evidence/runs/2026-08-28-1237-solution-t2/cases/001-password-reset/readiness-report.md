## What review found

### Raised by the first review, and sent to repair

- **request_reset takes a visibly different amount of time for registered vs. unregistered emails** (medium)
  - Requirement: OWASP Forgot Password Cheat Sheet: response to a reset request must not let an attacker distinguish registered from unregistered accounts, including via response-time side channels — the code path for both cases should take comparable time.
  - Evidence: app/auth.py request_reset(): for an unknown email it returns immediately (dict lookup only); for a known email it additionally calls new_token(), writes to self._resets, formats the link and calls mailer.send(). The comment says 'Don't reveal whether an email is registered' but only suppresses the response value, not the timing.
  - If shipped: An attacker can enumerate valid customer emails by measuring response latency of the forgot-password endpoint, enabling targeted credential-stuffing or phishing campaigns against confirmed accounts.

- **Older outstanding reset tokens for an account stay valid after a newer one is issued or after a reset already succeeds** (high)
  - Requirement: Password-reset token lifecycle best practice (OWASP Forgot Password Cheat Sheet / NIST 800-63B): issuing a new reset token or completing a reset should invalidate all other outstanding tokens for that account, since each represents a live credential.
  - Evidence: app/auth.py request_reset() always adds a new token to self._resets without removing/expiring any prior token for the same email; reset_password() only deletes the single token it consumed, leaving any other still-live token for that account usable.
  - If shipped: If an older reset email is intercepted, cached, or forwarded (e.g., via a compromised mailbox or shared inbox) after the legitimate user has already requested a newer link or already reset their password, the old token remains a valid, unused credential for up to 15 minutes — allowing account takeover after the rightful owner believes the account is secured.

- **reset_password has a check-then-act race that lets a single token be consumed more than once under concurrent requests** (medium)
  - Requirement: Single-use token invariant for password-reset tokens: a token must be consumable at most once, even under concurrent/duplicate submissions (this is the standard 'at-most-once' guarantee expected of any one-time credential, analogous to OAuth authorization codes).
  - Evidence: app/auth.py reset_password(): the token is looked up (self._resets.get), validated, and only deleted from self._resets after the password hash is written — there is no lock or atomic pop, so two concurrent calls with the same token can both pass validation before either deletion happens.
  - If shipped: Under a real multi-threaded/async account service, two near-simultaneous submissions of the same reset link (e.g., a user double-clicking, or a browser retry after a slow response) — or a race with an attacker replaying an intercepted link — can both 'succeed', producing a nondeterministic final password and violating the single-use contract the rest of the system relies on.

- **reset_password accepts any new_password, including empty string** (medium)
  - Requirement: NIST SP 800-63B / OWASP ASVS minimum password requirements (e.g., non-empty, minimum length) that any credential-setting endpoint — signup or reset — must enforce equally, so the reset path can't be used to bypass whatever policy exists elsewhere.
  - Evidence: app/auth.py reset_password() passes new_password directly to hash_password() with no length or emptiness check.
  - If shipped: A user (or attacker who obtains a valid token) can set the account password to an empty string or a trivially weak value, silently downgrading account security below whatever bar the normal signup flow enforces.

- **request_reset has no throttling, so it can be called unlimited times for the same email** (medium)
  - Requirement: OWASP Forgot Password Cheat Sheet requirement to rate-limit reset requests per account/IP to prevent abuse (email bombing) and to bound resource consumption.
  - Evidence: app/auth.py request_reset() unconditionally generates a token and sends mail on every call with no counter, cooldown, or per-email/per-IP limit.
  - If shipped: An attacker can flood a victim's inbox with reset emails (harassment/DoS against the user) or repeatedly hit the mail-sending path to exhaust downstream mail-service quota, with no code-level defense.

- **Expired or unused tokens are only ever removed from _resets when they happen to be looked up again** (low)
  - Requirement: Lifecycle management for time-bounded state: expired tokens must be purged (via TTL sweep or lazy cleanup on every relevant path) so stored state doesn't grow unbounded for the life of the process.
  - Evidence: app/auth.py: self._resets entries are deleted only inside reset_password() on expiry/success/missing-user paths. A token that is requested but never redeemed (the common case for the ~4/week manual resets this feature replaces, times any abuse volume) stays in the dict forever, since nothing sweeps it after expiry.
  - If shipped: Combined with the lack of rate limiting, repeated reset requests accumulate permanently in memory for the lifetime of the process, giving an attacker (or just normal usage over time) an easy unbounded-memory-growth vector against the account service.


### Still flagged after the repair pass

- **A valid, unexpired reset token is permanently destroyed on a recoverable validation failure (password too short)** (high)
  - Requirement: Forgot-password flow contract in the ticket: 'They click it and set a new password.' A reset link is expected to remain usable until it is successfully consumed or expires — OWASP Forgot Password Cheat Sheet treats the token as single-use only on a *successful* password change, not on client-side input validation failures.
  - Evidence: app/auth.py reset_password() calls `self._resets.pop(token, None)` unconditionally before checking `len(new_password) < self.MIN_PASSWORD_LENGTH`. Verified live: calling reset_password(token, 'short') returns False as expected, but a second call with the *same* token and a strong password also returns False and the password is never changed — the token was consumed by the first, failed attempt.
  - If shipped: A user who mistypes or picks a too-short password on their first try permanently loses their reset link. The form can't just show a validation error and let them retry — they are silently locked out and must go back to 'forgot password' and wait out the request cooldown for an entirely new email. This will generate exactly the kind of support tickets ACT-412 was meant to eliminate.

- **Reset tokens are stored as plaintext bearer credentials in the service's token store** (medium)
  - Requirement: OWASP Forgot Password Cheat Sheet: the reset token should be stored server-side only in hashed form (like a password or session token), precisely because it is a bearer credential that grants account takeover if disclosed.
  - Evidence: app/auth.py: `self._resets: dict[str, tuple[str, float]]` is keyed by the raw token returned by new_token(), and reset_password() does `self._resets.pop(token, None)` directly against the plaintext value — no hash of the token is stored or compared.
  - If shipped: Any compromise of the process's memory, a debug/error log that captures the token dict, or a backup/snapshot of this store hands an attacker fully-usable password-reset credentials for every outstanding request, with no additional verification step required.

- **Request cooldown is only enforced for registered emails, so requests against unregistered addresses are never rate-limited** (medium)
  - Requirement: OWASP Forgot Password Cheat Sheet requires rate-limiting of the reset-request endpoint regardless of whether the target account exists, both to prevent resource-exhaustion abuse and to avoid the throttle itself becoming a side channel for enumerating valid accounts.
  - Evidence: app/auth.py request_reset(): `if user is None: return` happens *before* the `_last_request` cooldown check/update, so `self._last_request` is never populated for unknown emails and the cooldown branch is unreachable for them — every call regenerates a token and re-does full expiry/link work with no throttling.
  - If shipped: An attacker can invoke request_reset for an unlimited number of non-existent addresses with no backoff, while real accounts are throttled to one email per 60s — a distinguishable behavioral asymmetry that can be used as part of an account-enumeration oracle, and a free amplification vector for wasting CPU/entropy on token generation at unlimited rate.

- **Concurrent request_reset calls for the same email can invalidate a token that was already emailed to the user** (medium)
  - Requirement: Check-then-act sequences (cooldown check, token invalidation, token store write, last-request write) that mutate shared state must be atomic under concurrent access for the service to behave correctly when called from multiple workers/threads or a double-submitted form — a property implied by the multi-worker deployment any production account service runs under.
  - Evidence: app/auth.py request_reset(): the cooldown read (`self._last_request.get(email)`), `_invalidate_tokens_for(email)`, and the writes to `self._resets`/`self._last_request` are not guarded by any lock. Verified: after two interleaved calls that both observe stale cooldown state, both emails are sent (mailer.sent length 2) but the first call's token is removed from `self._resets` by the second call's `_invalidate_tokens_for`, before it could ever be used.
  - If shipped: A user who double-clicks 'send reset link', or whose request hits two different app-server workers in a race, receives two reset emails where the first is already dead on arrival — they click the first (most recently received, if their mail client reorders) link and get a confusing 'invalid or expired token' error despite having just received it.

- **Email lookup for reset requests is case-sensitive, unlike normal email semantics** (low)
  - Requirement: RFC 5321/5322 treats the domain part of an email address as case-insensitive, and virtually every real mail and auth system in practice also treats the local part case-insensitively for account matching; users routinely type their address with different casing than at signup.
  - Evidence: app/auth.py request_reset(): `user = self.users.get(email)` is a raw dict lookup with no normalization. Verified: a user stored as 'Ada@Example.com' gets zero emails sent when requesting a reset as 'ada@example.com'.
  - If shipped: A legitimate, registered user who types their email in different case than it was stored gets no error and no email — indistinguishable (by design, for enumeration-resistance) from submitting an unregistered address, so they conclude the self-service flow is broken and go back to emailing support, defeating the point of the ticket.
