## What review found

### Raised by the first review, and sent to repair

- **No mutual exclusion for two concurrent requests carrying the same idempotency key** (high)
  - Requirement: Idempotency-key semantics (as implemented by Stripe and other payment APIs) require that a request with a key already 'in flight' be rejected or blocked (typically a 409 'request in progress') rather than allowed to proceed to the processor a second time. This is the exact 'two attempts at once' case the feature exists to close.
  - Evidence: app/charges.py post_charge: `record = self._idempotency_keys.get(idempotency_key)` is read, then `_execute` is called, then the record is written -- a classic check-then-act gap. Nothing marks the key as 'in progress' before `_execute` runs, so two requests that arrive close together (e.g. the mobile client's automatic retry firing before the first response returns -- the scenario the ticket itself describes) both find no record, both call `_execute`, and both append to `self.executed`.
  - If shipped: A customer is charged twice from two nearly-simultaneous requests carrying the identical idempotency key -- precisely the double-charge support ticket this feature was built to eliminate, just moved from 'sequential retry' to 'concurrent retry'.

- **A transient processor failure (5xx) is cached and permanently returned to all future retries with that key** (high)
  - Requirement: Documented idempotency-key behavior (Stripe API) explicitly does not persist an idempotent result for a request that resulted in a 500-range/processor error; such failures are meant to be safely retryable with the same key. Only completed, deterministic results (2xx, or a definitive 4xx) should be locked in.
  - Evidence: app/charges.py post_charge caches whatever `_execute` returns unconditionally: `self._idempotency_keys[idempotency_key] = {"status": status, "body": body, ...}` runs the same way whether status is 200 or 500. Verified: after a first attempt with `simulate="processor_down"` returns 500, a later retry with the same key and corrected params returns 409 ('different parameters') because the failed attempt's params (including the stale `simulate` flag) are frozen in the record -- there is no way to ever successfully charge with that key again.
  - If shipped: After any transient upstream outage, the client is permanently stuck: retrying with the same key returns the cached failure forever, and retrying with different/corrected params returns a 409. The only escape is generating a brand-new idempotency key, which the client has no way of knowing it needs to do -- this converts one class of support ticket (double charge) into another (payment permanently stuck / customer can't be charged even when the processor has recovered).

- **Idempotency records never expire and the store grows unboundedly** (medium)
  - Requirement: Published idempotency-key specs (Stripe: 24-hour key lifetime) bound how long a key is honored, both to allow legitimate key reuse after the window and to bound server-side storage. The ticket's explicit instruction to source time from the injected `Clock` (not `time.time()`) is a strong signal that time-based expiry was expected.
  - Evidence: app/charges.py stores `"at": self.clock.now()` on every record but never reads it back anywhere -- there is no expiry check in `post_charge`, and `self._idempotency_keys` is a plain dict with no eviction.
  - If shipped: In production this dict is process-lifetime, unbounded, and keyed by client-supplied strings -- an ever-growing memory leak, and legitimate key reuse after a reasonable window (e.g. a customer paying again a week later using an SDK that reuses UUIDs from a pool) is permanently blocked with a 409 instead of being allowed to proceed as a fresh charge.

- **If the upstream call raises instead of returning, the idempotency record is never written and a retry re-charges** (high)
  - Requirement: The ticket's own invariant: 'self.executed is the ledger of what the upstream processor actually attempted. One entry = money moved once' implies that any code path where `_execute` has been entered (and thus may have moved money) must be captured by the idempotency layer before it can be retried.
  - Evidence: app/charges.py post_charge calls `status, body = self._execute(params)` with no try/except; the idempotency dict is only populated in the lines immediately after that call returns normally. `_execute` explicitly documents that once entered, 'the attempt is on the ledger whether or not it succeeded' -- i.e. it's expected to be able to fail/throw for reasons other than a clean 500 (e.g. a network exception talking to the real processor). Any such exception unwinds `post_charge` with no idempotency record persisted.
  - If shipped: A network-level failure between the service and the real payment processor (the single most common failure mode for a payments integration) leaves an entry in `self.executed` (money may have moved) but no idempotency record. The client's automatic retry with the same key then sees no record, calls `_execute` again, and the customer is charged twice.

- **Idempotency records live only in process memory and are lost on restart/deploy** (medium)
  - Requirement: A payments idempotency guarantee must survive the process that handled the original request, since deploys, autoscaling, and crashes routinely rotate the process/instance that a retry lands on.
  - Evidence: app/charges.py: `self._idempotency_keys: dict[str, dict] = {}` is an instance attribute of `ChargeAPI` with no persistence layer; nothing here writes the record anywhere durable.
  - If shipped: A deploy or worker restart between the original charge and the client's retry (a very plausible window, since the ticket describes retries triggered by dropped connections) wipes the idempotency table; the retry lands on a fresh process with no memory of the key and charges the customer again -- the same failure class the feature is meant to close.

- **An empty-string idempotency key is accepted and treated as a real, distinct key** (low)
  - Requirement: Boundary handling for a client-supplied identifier: an empty string is not a meaningful idempotency key and should be treated the same as 'no key supplied' (or rejected), not silently accepted as valid deduplication state.
  - Evidence: app/charges.py checks `if idempotency_key is not None`, so `idempotency_key=""` passes the guard and is used as a real dict key in `self._idempotency_keys`.
  - If shipped: A client bug that sends `""` instead of omitting the header gets silent, unintended deduplication behavior (or a spurious 409 on the next such request) instead of a clear validation error, making the failure mode hard to diagnose.


### Still flagged after the repair pass

- **On a mid-charge exception the idempotency key is deleted and a retry starts a brand-new, unprotected attempt** (high)
  - Requirement: Idempotency-key semantics for payment APIs (the model this ticket follows, e.g. Stripe's Idempotent Requests): when the outcome of contacting the processor is unknown (timeout / connection drop / crash), the key must NOT be treated as free-for-reuse, because the underlying charge may have already succeeded. Only requests that are known to have produced no side effect may be safely retried as brand-new.
  - Evidence: app/charges.py:84-91 calls self.before_execute() -- documented as the extension point Ops uses to 'inject latency and to replay traffic', i.e. simulate exactly the network conditions the ticket describes -- BEFORE appending to self.executed. If before_execute (or anything before line 91) raises, the except block at 132-140 pops the idempotency key and re-raises, with no record in self.executed and no memory that this key was ever attempted.
  - If shipped: The exact scenario in the ticket -- the client's connection drops during a charge and the SDK auto-retries -- maps to precisely this code path when the drop happens on our side talking to the processor. Because the key is deleted, the retry is treated as a fresh charge and calls _execute again. If the original attempt actually reached and was processed by the processor before the exception was raised, the customer is billed twice, and self.executed only shows one entry, so the ledger the ticket asks engineers to trust hides the double charge.

- **A key claimed 'in_progress' has no timeout and is never released if the process dies or before_execute hangs** (high)
  - Requirement: An idempotency lock must have a bounded lifetime independent of the 24h key TTL; the TTL check for the record is only run for records whose status != 'in_progress'.
  - Evidence: app/charges.py:109-112 gates the TTL expiry check on record['status'] != 'in_progress', and 113-117 returns 409 whenever status == 'in_progress'. The only code paths that ever clear an in_progress record are the success path (142-154) and the exception path (137-139) of the SAME call that created it -- there is no independent lock timeout.
  - If shipped: If the process is killed mid-charge (OOM, deploy, orchestrator restart) -- explicitly a supported case per the docstring recommending a durable MutableMapping 'to survive process restarts/deploys' -- the in_progress record survives the restart with nothing left to clear it. Every subsequent request with that idempotency key gets a permanent 409 forever, even after the 24h window the ticket relies on for key reuse. The customer can never complete that charge with that key and support has no self-service recovery path.

- **Comment claims the 24h TTL 'bounds storage', but expired records are only evicted lazily on exact-key lookup** (medium)
  - Requirement: A stated storage-bounding mechanism must actually bound storage; otherwise the durable store (which the docstring explicitly recommends for production use) grows without limit.
  - Evidence: app/charges.py:15-17 comment: 'Stripe-style 24h idempotency key lifetime: bounds storage'. But the only eviction logic (lines 109-112) runs inside post_charge and only fires when that specific key is looked up again after expiry. Keys that are used once and never retried are never removed.
  - If shipped: In production, most idempotency keys are used exactly once and never looked up again. With no background sweep, the durable store (shelve/disk-backed, per the class docstring's own recommendation) grows unbounded with every charge ever made, contradicting the stated bounding rationale and eventually causing disk/memory exhaustion or unbounded cost on the backing store.

- **idempotency_key accepts any string with no length or character validation** (low)
  - Requirement: Published idempotency-key contracts (e.g. Stripe limits keys to 255 characters) bound key size specifically to prevent unbounded storage/log growth per request.
  - Evidence: app/charges.py:104, `key = idempotency_key or None`, is the only normalization applied to the incoming key before it is used as a dict key and stored verbatim in `_idempotency_keys` (line 125-130 / 149-154), with `params` and `body` copied alongside it.
  - If shipped: A malformed or malicious client can send an arbitrarily large string as the idempotency key on every request; each becomes a permanent (until TTL-lookup-eviction, which per the prior finding may never happen) entry in the store, including a durable on-disk store, giving an attacker or buggy client a cheap way to inflate storage and degrade the service.
