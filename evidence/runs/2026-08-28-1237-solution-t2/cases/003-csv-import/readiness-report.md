## What review found

### Raised by the first review, and sent to repair

- **Only comma-delimited CSV is accepted; semicolon-delimited exports fail entirely** (high)
  - Requirement: Ticket states 'The files come from the customer's own systems — HR exports, spreadsheets, whatever they've got — so we don't control how they're produced.' A large share of Excel exports in non-US locales (most of Europe) default to semicolon as the field separator because comma is the decimal separator. RFC 4180 itself doesn't mandate comma, and real-world CSV producers vary.
  - Evidence: app/importer.py:43 hardcodes `csv.reader(io.StringIO(text))` with no dialect sniffing (e.g. `csv.Sniffer`). Verified: `import_users('email;name;team\nada@example.com;...')` returns zero users and the error 'Missing required column(s): email, name, team' — the entire file is rejected, not just malformed rows.
  - If shipped: An admin uploading a perfectly valid export from a European customer's HR system gets a total failure with a misleading 'missing column' error, even though the columns are right there separated by semicolons. This directly contradicts the ticket's premise that varied customer-produced files must be handled.

- **Duplicate column names in the header silently overwrite each other with no error** (medium)
  - Requirement: Contract states result.users must be 'keyed by the header column names' and that unimportable rows must be reported in errors — implicit requirement that data isn't silently lost or misattributed when it can't be unambiguously mapped.
  - Evidence: app/importer.py:69 builds the record via `zip(header, row)` into a plain dict. Verified: header `email,name,team,email` with row `a@x.com,Ada,Eng,a2@x.com` produces a single user with email `a2@x.com` — the first email column's value is silently discarded and no error or warning is emitted.
  - If shipped: If a customer's export has a duplicate or renamed-but-colliding column (common in hand-edited HR spreadsheets, e.g. two 'email' columns for personal/work), the importer picks whichever comes last and never tells the admin data was dropped, potentially importing the wrong email address for a user account.

- **Duplicate emails within the same file are imported as separate users with no error** (medium)
  - Requirement: Ticket: 'Rows that can't be imported get reported back to the admin.' A row creating a user with an email already claimed by another row in the same batch cannot be validly imported as a distinct account and should be flagged, since email is presumably the unique identifier for a user record.
  - Evidence: app/importer.py has no dedup/uniqueness check across rows. Verified: two rows with `a@x.com` both pass through into `result.users` with no error.
  - If shipped: The admin UI/downstream user-creation step receives two 'create user' records for the same email; depending on how that layer handles conflicts, the second either silently overwrites the first, errors out for reasons the admin never sees explained here, or creates inconsistent state — none of which is surfaced back through the reported errors this feature promises.

- **Required-column check is case-sensitive and only trims outer whitespace** (medium)
  - Requirement: Ticket premise: files are customer-produced and uncontrolled ('whatever they've got'). A bulk import that must tolerate arbitrary customer formatting should not fail solely because a header cell reads 'Email' instead of 'email'.
  - Evidence: app/importer.py:50-56 strips whitespace but does no case normalization before comparing against REQUIRED_COLUMNS. Verified: header `Email,Name,Team` triggers 'Missing required column(s): email, name, team' even though all three columns are present under different casing.
  - If shipped: A customer's HR export with Title-Case or ALL-CAPS headers (extremely common) is rejected outright with zero rows imported, forcing the admin to manually edit the source file before every upload — defeating the purpose of accepting arbitrary customer exports.

- **No limit on row count or file size before processing** (low)
  - Requirement: General availability/robustness expectation for an admin-facing file upload endpoint accepting externally-produced files: unbounded input must not be able to exhaust server resources on a single request.
  - Evidence: app/importer.py reads the entire csv_text into memory (io.StringIO) and iterates every row into result.users/result.errors with no cap on row count or total size.
  - If shipped: An oversized or malformed file (accidentally or intentionally, e.g. a multi-GB export or a file with millions of blank-looking rows) is processed in full in one request, risking memory exhaustion or a hung request on the admin service — a low-effort denial-of-service vector for a feature explicitly built to accept files the team does not control.


### Still flagged after the repair pass

- **Email column is only checked for non-emptiness, never validated as an email** (high)
  - Requirement: A bulk user-import feature that reports 'rows that can't be imported' must validate the semantic correctness of the identifying field (RFC 5321/5322 email syntax), not just its presence — otherwise garbage values silently become account identifiers.
  - Evidence: app/importer.py: the only check on `record['email']` is `empty_required` (non-blank). Verified: `import_users('email,name,team\nnot-an-email,Bob,Eng\n')` returns the row in `result.users` with `email: 'not-an-email'` and no error.
  - If shipped: Any garbage string in the email column (typos, 'N/A', a name pasted into the wrong column) becomes a user record with an invalid email and is silently accepted instead of being reported to the admin. Downstream invite/notification emails will bounce or never send, and the admin has no signal from the import that anything was wrong.

- **Untrusted cell values starting with =, +, -, @ are passed through unsanitized into user records** (high)
  - Requirement: OWASP CSV Injection / Formula Injection guidance (CWE-1236): data originating from an untrusted, customer-controlled file that may later be opened in Excel/Sheets or re-exported as CSV must have leading formula-trigger characters neutralized or flagged, since spreadsheet applications execute cell content beginning with =, +, -, or @.
  - Evidence: app/importer.py builds `record` via a straight `.strip()` of each cell with no sanitization; verified `import_users('email,name,team,notes\nada@example.com,Ada,Eng,=cmd|/c calc!A0\n')` returns the formula string unmodified in `result.users[0]['notes']`. The ticket explicitly states 'any other columns come through as-is' from files the team does not control.
  - If shipped: If an admin exports the resulting user list back to CSV/Excel for review (a common admin-UI action), a malicious or corrupted customer export can trigger arbitrary formula execution (including OS command execution via DDE/cmd formulas) on the admin's machine — a well-known, actively exploited attack class. A security reviewer would block sign-off on this under CWE-1236.

- **Reported error line numbers are wrong once any earlier row contains a quoted multi-line field** (low)
  - Requirement: Error messages returned to the admin must reference the actual physical line in the uploaded file (a basic usability/correctness requirement for 'rows that can't be imported get reported back to the admin') so the admin can locate and fix the bad row.
  - Evidence: app/importer.py uses `enumerate(reader, start=2)`, counting *logical CSV rows*, not physical file lines. Verified: with a valid row containing an RFC-4180 quoted embedded newline (physical lines 2-3), the next bad row is on physical line 4 but is reported as 'Row 3'.
  - If shipped: Admins with legitimately quoted multi-line fields (e.g. addresses, notes) get error messages pointing at the wrong line, making it harder to locate and fix bad rows in larger files, increasing support burden.
