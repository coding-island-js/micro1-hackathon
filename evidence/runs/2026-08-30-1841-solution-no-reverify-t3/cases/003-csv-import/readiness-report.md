## What review found

### Raised by the first review, and sent to repair

- **Non-LF line endings (bare \r) crash the import with an unhandled exception** (high)
  - Requirement: The ticket's own stated context — 'the files come from the customer's own systems... whatever they've got' — requires the importer to tolerate malformed/legacy export formats and report problems via ImportResult.errors, not raise. Python's csv module explicitly documents that iterables without proper newline handling can raise `_csv.Error: new-line character seen in unquoted field`.
  - Evidence: app/importer.py:45-48 builds `csv.reader(io.StringIO(text))` with no exception handling around `next(reader)` or the row loop. A CSV using old Mac-style `\r`-only line endings (still produced by some legacy HR/export tools) causes `_csv.Error: new-line character seen in unquoted field - do you need to open the file with newline=''?` to propagate out of `import_users` uncaught, verified by direct reproduction.
  - If shipped: The admin upload request fails with a raw 500/unhandled exception instead of a per-row error list. The whole file — potentially all 340 users — fails to import with no usable feedback, contradicting the ticket's core promise that bad rows are reported and the rest of the file still imports.

- **Required column detection is case-sensitive, rejecting valid customer headers** (high)
  - Requirement: Implicit requirement from the ticket that customer-produced files ('HR exports, spreadsheets, whatever they've got') must be accepted when they contain the required data — CSV header names are commonly capitalized (e.g. 'Email', 'Name', 'Team') by Excel exports and HR systems, and a robust importer must not treat casing as a hard failure.
  - Evidence: app/importer.py:53-57: `columns = [c.strip() for c in header]` only strips whitespace, then `missing = [c for c in REQUIRED_COLUMNS if c not in columns]` does an exact case-sensitive string comparison against lowercase `REQUIRED_COLUMNS`. A header of `Email,Name,Team` is reported as fully missing all three required columns even though they are present, verified by reproduction.
  - If shipped: Any customer file with title-cased or upper-cased headers is rejected outright with zero users imported, even though the data is well-formed — forcing the admin to manually edit the CSV before every upload, defeating the purpose of the bulk-import feature.

- **Duplicate emails within the same file are silently imported as separate records** (medium)
  - Requirement: A bulk user-provisioning import must treat email as the unique key for account creation (implicit from 'add users' semantics and from any downstream user-creation API that would reject/collide on a duplicate email) — duplicates should be flagged as unimportable, not passed through twice.
  - Evidence: app/importer.py:69-84 has no tracking of previously-seen emails; two rows with the same email (e.g. a re-listed employee in an HR export, or the same person on two teams) both land in `result.users` unchanged, verified by reproduction (`ada@example.com` appears twice with different names/teams and no error).
  - If shipped: Downstream account creation either silently overwrites the first row's data with the second (whichever the caller applies last) or throws a uniqueness-constraint error that aborts the whole batch outside the importer's error-reporting contract, so the admin never sees a clean per-row report of what actually happened for that user.

- **Cell values beginning with =, +, -, @ are stored/passed through unsanitized** (medium)
  - Requirement: OWASP CSV Injection guidance for data originating from untrusted/customer-controlled sources: values beginning with formula-trigger characters must be neutralized (e.g. prefixed) before being stored or re-displayed/re-exported, since the ticket explicitly states these files are customer-produced and not controlled by the vendor.
  - Evidence: app/importer.py:69-84 strips whitespace but performs no sanitization on the `name`/`team`/extra-column values. A row with `name` = `=cmd|' /C calc'!A0` is accepted into `result.users` verbatim, verified by reproduction.
  - If shipped: If any admin tool later exports these user records back to CSV/Excel (a common pattern for user-management admin UIs), opening that file executes the embedded formula/DDE payload on the admin's machine — a classic CSV/formula-injection attack vector a security reviewer would block on.

- **A repeated header column name silently drops the earlier value with no error** (low)
  - Requirement: The contract states rows/data that can't be correctly imported must be reported in `errors`; silently discarding a valid field's value due to a header collision is a correctness violation of that contract, not merely a formatting quirk.
  - Evidence: app/importer.py:69: `record = dict(zip(columns, ...))` — if the header contains the same column name twice (e.g. a stray extra `email` column from a customer export merge), the second value silently overwrites the first in the dict with no error emitted, verified by reproduction: header `email,name,team,email` with values `ada@example.com,...,second@example.com` produces a user record with email `second@example.com` and no diagnostic.
  - If shipped: The admin sees a clean 'no errors' import while a user is silently created with the wrong email address, with no indication in `result.errors` that data was lost — a correctness bug that is invisible until someone can't log in.
