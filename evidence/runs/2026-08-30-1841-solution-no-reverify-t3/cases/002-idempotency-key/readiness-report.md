## What review found

### Raised by the first review, and sent to repair

- **Concurrent requests with the same idempotency key both execute the charge** (high)
  - Requirement: Idempotency-key semantics (as implemented by Stripe and every payments API this pattern imitates) require that a second request with the same key, arriving while the first is still in flight, be blocked or made to wait for the first result (typically a 409 'request outstanding') rather than being allowed to independently execute. The check-then-store logic here is not atomic and holds no lock across `_execute`.
  - Evidence: app/charges.py:90-102 — `if idempotency_key in self._idempotency_cache: return ...` is checked, then `_execute` runs, then the cache is populated afterward. Nothing marks the key as 'in progress' before `_execute` runs. Reproduced with two threads sharing one ChargeAPI racing on the same key: both got 200 and `len(api.executed) == 2` — two separate ledger entries for one logical request.
  - If shipped: This is precisely the double-charge scenario PAY-208 was opened to fix, just triggered by request concurrency (mobile client double-tap, retry racing the original before it returns, load balancer replaying) instead of a dropped connection. The customer is billed twice and support gets a fourth double-charge ticket.

- **Reusing a key with different request parameters returns the original charge with no error** (high)
  - Requirement: Idempotency-key contracts (Stripe's documented behavior for this exact feature) require rejecting a replayed key whose request body differs from the original with an idempotency error, precisely to catch client bugs that reuse a key across two logically different charges.
  - Evidence: app/charges.py:90-91 — the cache is keyed only on `idempotency_key`; `params` is never compared against what was stored for that key on a cache hit.
  - If shipped: Verified: posting amount=2500 with key 'k1' then amount=9999 with the same key returns the cached $25.00 result for the $99.99 request, silently. A client-side bug that reuses a key (e.g. a stale key cached client-side across two different cart totals) results in the wrong amount being reported as charged with no error surfaced — a billing-integrity bug that is invisible to both client and server.

- **A transient processor failure (5xx) is cached forever, permanently blocking retry on that key** (high)
  - Requirement: Idempotency keys must not permanently lock a client out of a legitimate retry after a transient/definitive-failure response from the processor; production idempotency stores expire entries (Stripe: 24 hours) so a key becomes usable again. The ticket explicitly calls out the injected `Clock` for time-based logic, implying expiry was expected.
  - Evidence: app/charges.py:99-100 stores `(status, body)` in `self._idempotency_cache` unconditionally, including `status == 500` responses, with no TTL and no use of `self.clock` anywhere in `post_charge`.
  - If shipped: Verified: a first attempt with `simulate=processor_down` returns 500; advancing the clock 10 days and retrying the same key still returns the identical stale 500 with the same `ref`, and `len(api.executed)` stays at 1 forever — the processor is never contacted again. The exact retry behavior the ticket says the mobile SDK performs automatically becomes permanently useless for any key that first hit a processor outage; the customer can never complete that charge unless the client mints a new key, which reintroduces the original double-charge risk this ticket exists to close.

- **Idempotency cache never expires or evicts entries** (medium)
  - Requirement: Published idempotency-key implementations bound key lifetime (Stripe: 24 hours) both for correctness (allow retry after a window) and operational safety (bounded memory). Nothing here bounds `self._idempotency_cache`.
  - Evidence: app/charges.py:58, 99-100 — `_idempotency_cache` is a plain dict with entries added on every keyed request and never removed.
  - If shipped: In a long-lived process handling production charge volume, this dict grows without bound, an unbounded memory leak that eventually degrades or crashes the service — a service-availability issue distinct from the correctness issue above.
