## What review found

### Raised by the first review, and sent to repair

- **Reset requests are matched against the user store with a raw, case-sensitive dict key** (medium)
  - Requirement: RFC 5321 treats the domain part of an email address as case-insensitive, and in practice mailbox providers and most user stores treat the whole address case-insensitively for login/lookup purposes; a forgot-password flow must find the account regardless of the case the user typed.
  - Evidence: app/auth.py:95 does `if email not in self.users: return` with no normalization (no `.lower()`/`.strip()`) before the dict lookup, and `reset_password` (line 123) does the same `self.users.get(email)`.
  - If shipped: A user who signed up as ada@example.com but types Ada@Example.com (common on mobile keyboards with autocapitalize) gets silently no email and no error, so they conclude the feature is broken and file another support ticket -- the exact outcome ACCT-412 exists to eliminate.

- **Unknown vs. known emails take a different code path with observably different work** (medium)
  - Requirement: OWASP ASVS / common password-reset guidance: the endpoint must behave identically (constant response shape and timing) for existing and non-existing accounts to prevent account enumeration.
  - Evidence: app/auth.py:94-111 returns immediately for an unknown email (`if email not in self.users: return`) doing no token generation, no dict writes, and no mailer call, whereas a known email does all of that -- a measurable timing and side-effect difference.
  - If shipped: An attacker probing the endpoint (directly or through whatever thin HTTP wrapper calls this service) can distinguish registered from unregistered emails by response latency or by monitoring whether mail was queued, enabling account enumeration for credential-stuffing target lists.

- **Reset token is looked up via plain dict indexing instead of a constant-time comparison** (low)
  - Requirement: The project's own security posture (evidenced by `verify_password` using `secrets.compare_digest`) treats secret comparison as needing to be timing-safe; the same standard applies to bearer reset tokens, which are the sole authentication factor for the reset step.
  - Evidence: app/auth.py:114 does `self._resets.get(token)` -- a hash-bucket lookup with no constant-time guarantee over the token string itself, unlike `verify_password` (line 24) which explicitly uses `secrets.compare_digest`.
  - If shipped: In principle allows a timing side-channel on token guessing; more importantly it's an inconsistency a security reviewer will flag on inspection since the same file demonstrates the team knows to use `compare_digest` for exactly this kind of secret comparison and didn't apply it here.

- **Check-then-delete on token use is not atomic, so a token can be redeemed twice under concurrent requests** (medium)
  - Requirement: A one-time-use credential (the reset token) must be consumed atomically: 'redeem exactly once' is a basic requirement for any single-use token, analogous to the double-spend problem in payment tokens.
  - Evidence: app/auth.py:113-130: `reset_password` does `entry = self._resets.get(token)`, validates expiry/user, then later `del self._resets[token]`. Two concurrent calls with the same token can both pass the `entry is None` and expiry checks before either deletes the entry.
  - If shipped: If the service is ever run under a threaded/async server (the standard deployment for a Python web app), two simultaneous submissions of the same reset link -- e.g. a user double-clicking, or an attacker racing a legitimate request -- can both succeed, each writing `password_hash`, with no guarantee about which value ends up live and no indication to the user that a race occurred.

- **Expired, unused reset tokens are never purged except on next request for the same user or on lookup of that exact token** (low)
  - Requirement: State with a defined TTL (`TOKEN_TTL_SECONDS`) must be reclaimed once it expires; an in-memory store that only prunes an entry when it happens to be looked up again is not bounded by its own stated expiry policy.
  - Evidence: app/auth.py:92-104: `_resets` is only cleaned for a given email when that same email calls `request_reset` again, or for a given token when `reset_password` happens to be called with it. There is no sweep of entries whose `expires_at` has passed without ever being touched again.
  - If shipped: In production, most requested resets are never completed (users ignore the email, or use a support-driven reset instead) and never revisited, so `_resets` grows without bound over the life of the process -- a slow memory leak that eventually degrades or crashes the account service.
